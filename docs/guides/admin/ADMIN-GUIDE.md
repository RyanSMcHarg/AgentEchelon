# Admin Console Guide

How operators use the AgentEchelon admin dashboard to check platform health, review how the assistants are performing, and administer conversations. Written to be portable - it describes behavior, not any specific AWS account.

## Deployment decisions

Before you operate the console, a handful of **deploy-time** choices decide what this dashboard shows and what you can do in it. None is a one-way door - you can change most later with a redeploy - but picking deliberately up front saves rework. This is the orientation; each row links to the guide that owns the how-to. The full context flag reference is the Configuration section of [`README.md`](../../../README.md#configuration).

**Configurations.** In the design a deployment declares its capabilities in one `capabilities` list and each configuration adds to the one before: an anonymous visitor in the widget with one assistant and no accounts; then accounts and the chat app (`chat`, with the deployment's own user pool as an issuer); then the admin backend and console (`admin`, which needs an issuer other than the guest issuer); then email (`notifications`); then meetings (`meetings`); then more identity providers and host sites; then connectors (`connectors`). A capability that is not declared leaves no stack, route or setting behind, so a deployment without `admin` has no admin backend and this console has nothing to call. The list is read today (`backend/lib/config/capabilities.ts`): `chat`, `admin`, `notifications`, `experiments`, `battle`, `operations`, `connectors` and `widget` are built, and a deployment without `admin` has no admin read plane, admin notification channel or console hosting. **NOT BUILT:** a deployment without accounts, since the core still creates every classification's assistant stack. See [STACKS.md](../../overview/STACKS.md#layers-and-capabilities).

**A sensible first deployment:** Athena mode, built-in Cognito, `/battle` on, a verified `senderEmail`, WAF on. That gives you the Operations / Performance / Oversight / Models / Assistants / Experiments / Users console with archival and client-event health, and nothing that needs a VPC. The Evaluation dashboard, Flagged, Ground Truth, an experiment's results and battles, and the Alerts tab are Aurora-only, so turn on Aurora mode when you want the advanced quality/telemetry views - it's a `--context` flag, not a migration. After deploying, create your first `admins` user ([After a fresh deploy](#after-a-fresh-deploy)).

### After a fresh deploy

A fresh deployment has a new user pool and a new Amazon Chime SDK app instance, so it has no people. Re-provision from `backend/`, with `AE_INSTANCE_NAME` set to the instance and `TEST_SECRET_NAME` set to that instance's test secret, in this order. Every step is idempotent, and `provision-admin.mjs`, `provision-test-users.mjs` and `seed-demo.ts` each take `--dry-run`, which makes no AWS call and prints what the run would do.

1. **First admin.** `ADMIN_EMAIL=<address> ADMIN_TIER=<classification> node scripts/provision-admin.mjs` creates the admin in `admins` and the named classification group, in `FORCE_CHANGE_PASSWORD`. The admin has no AppInstanceUser yet: only the credential exchange creates a person, at their first sign-in.
2. **Admin sign-in.** The admin signs in to the chat app or the console once and sets their own password. That sign-in calls the credential exchange, which mints their AppInstanceUser. Steps 3 to 5 do not wait on it; step 6 does.
3. **Test users.** `node scripts/provision-test-users.mjs` creates the e2e users with a permanent password, writes the secret, then signs each user in through the credential exchange and records the `userArn` it answers with beside the login.
4. **Demo users.** `npx ts-node scripts/seed-demo.ts` creates the demo users, signs each in through the exchange, and writes `testAdmin`, `basicUser`, `standardUser` and `premiumUser` into the secret with each `userArn`. A user the exchange names no person for fails the run, after the secret holds the password, so a re-run converges.
5. **Validate.** `node scripts/validate.mjs` runs the full e2e pass. Its `seed` phase runs `seed-demo.ts` again, which changes nothing that step 4 set.
6. **Recipients.** `briefingRecipientArns` and `alertRecipientArns` in `deploy.config.json` take AppInstanceUser ARNs, so they stay empty on the first deploy: with none, the proactive briefing runs and sends nothing, and the archival alarm and its notifier are not created. After step 2, run `ADMIN_EMAIL=<address> node scripts/provision-admin.mjs --print-arn`; it reads the admin's Identities row, prints their AppInstanceUser ARN and changes nothing in the pool. A full re-run never resets an existing admin's password either: with `ADMIN_TEMP_PASSWORD` set it resets the password only when `--reset-password` is also passed. Put each recipient's ARN in the keys, comma-separated, then deploy the stacks that read them: `npm run deploy:stack -- <prefix>Notifications --diff-only`, then the same without `--diff-only`. Both read them from the one `Notifications` stack, in either archive mode.

## Access

The console is its **own app served from its own origin**, separate from the chat SPA (which carries no admin code or endpoints). Signing in requests a **console session** from the admin credential exchange (in `AdminServices`): a person whose groups resolve to the deployment's admin-plane classification receives the `admins` console role, a member of `team-members` receives the team role scoped to the assistants their team owns, and anyone else is refused and sees an access-denied screen, never the console. Group membership is authoritative; `custom:tier` does not grant admin. Every admin route is `AWS_IAM`-authorized except the console session request itself, which is behind `AdminApi`'s edge authorizer: the console SigV4-signs each call with its session, and API Gateway refuses a role that does not hold that route's capability (`backend/lib/config/admin-capabilities.ts`) before any handler runs. The console renders against the capabilities the session reports, and a refused call names the capability it lacked. When `VITE_ADMIN_APP_URL` is set, the chat header shows an admin a plain link out to the console (admin-only, new tab) - a URL, not embedded admin code. [`ADMIN-INTEGRATION-GUIDE.md`](ADMIN-INTEGRATION-GUIDE.md) describes the mechanism in full.

Knowing **which human a participant is**, as against only that a participant acted, is a narrower grant than admin. The conversation reads return no participant name to anyone: the messages, the membership and the timeline carry the participant's ARN on every row and no name, whoever asks. Resolving those ARNs to names is a separate call, `GET admin/conversations/identities`, behind the `see-user-identity` capability, which the catalog grants to the `admins` console role only. The name is worth its own grant because it identifies the person: the credential exchange creates the Amazon Chime SDK `AppInstanceUser` at the person's first sign-in and names it from the IdP's `name` claim when the token carries one, otherwise from the local part of their email address, never the full address, falling back to the person id (`displayNameFor` in `backend/lambda/src/lib/person-identity.ts`), so a participant's name here is a **personal name or an email local part**, not a nickname. API Gateway refuses the identity call to a role without the capability - it is the only thing that resource authorizes, so the refusal is the gateway's and not the handler's. Narrowing who sees names is a change to the catalog. `USER_IDENTITY_VIEW_GROUP_NAMES` is a second, handler-side group check (`callerCanSeeUserIdentity` in `backend/lambda/src/lib/auth.ts`) that binds only on a call the edge authorizer admitted, and no admin conversation route is behind the edge authorizer. A caller refused the identity call still reads the conversation in full; the console keeps showing ids.

## Who signs in, and what their groups give

People sign in through the identity providers the deployment declares in its trusted-issuer registry: the deployment's own user pool, an organization's OIDC provider verified directly (Okta, Auth0, Microsoft Entra ID), or a SAML or OIDC provider federated into the pool. How to declare one is [IDENTITY-PROVIDER-GUIDE.md](../user/IDENTITY-PROVIDER-GUIDE.md); what follows is what an administrator does once it is declared.

**Access is granted and removed at the provider, through its groups.** Each provider's registry entry translates the provider's groups into the deployment's own **AgentEchelon groups**, and those decide everything a person reaches:

- a clearance group (shipped: `basic`, `standard`, `premium`) clears them for that classification's conversations;
- `admins` gives them this console as an administrator;
- `team-members` with a `team-<name>` group, beside a clearance group, gives them this console scoped to the assistants that team owns, and the console names them by their team ("Ops team, owner of the ops-premium assistant"). They create assistants for their own team and move an owned assistant between their own teams; a team that owns none yet sees Assistants alone, where it creates one. A team may own several assistants, up to about 30 to 35: each owned assistant is named in the member's console session, whose policy AWS limits to 2,048 characters. A team past that is refused a console session with `TEAM_SCOPE_TOO_LARGE`; split its assistants across two teams. The sample deployment shows this with the Ops team, which owns the Ops assistant (`ops-premium`, `ownerTeam: 'ops'` in the shipped profiles), and the test users `testuser-team-ops@` (in `team-ops`) and `testuser-team-none@` (in no team, so refused);
- a membership group (shipped: `ops`) grants nothing by itself.

The full table, with what each needs, is [The access each AgentEchelon group gives](../user/IDENTITY-PROVIDER-GUIDE.md#the-access-each-agentechelon-group-gives). Each entry's `classifications` bound what its people can reach, whatever their groups, and a provider group the entry does not map reaches nothing, even one the provider calls `admins`.

- **To give someone access:** a person on the deployment's own pool goes into the group in the Users tab; a person from a provider goes into the provider group the entry maps, in the provider's own console. They reach it at their next sign-in.
- **To take it away:** remove them from that group. The first token issued after the removal carries what they hold then; the token they hold and a session already vended keep their role until they expire. For an immediate removal, offboard them from the Users tab, which erases the person for every issuer ([ADR-058](../../design/decisions/058-offboarding-runs-by-app-instance-user-for-every-issuer.md)).
- **To make someone an administrator through a provider:** the entry declares `admin: true` and maps one of the provider's groups to `admins`; then add them to that provider group.

**NOT RUN:** `tests/e2e/a-providers-groups-give-the-access-the-guide-describes.spec.ts` (a mapped group's classification, a mapped `admins` group's console session, an unmapped `admins` group reaching nothing, and removal taking effect with the next token) has not yet passed against a deployment. **NOT BUILT:** the admin notification channel's members are read by listing a pool group's members, so an administrator whose `admins` group is translated from a provider, verified directly or federated into the pool, reaches the console but receives no admin alerts. The Users tab lists every person and offboards any of them, but approves, changes clearance and edits groups for accounts on the deployment's own pool alone ([ADR-021](../../design/decisions/021-user-administration-is-not-idp-abstracted.md)).

## Navigation

The dashboard uses a two-level nav - a **section rail** across the top of its seven sections, and **sub-tabs** within a section when it has more than one view. A **date-range selector** (24h / 7 / 30 / 90 days) in the header scopes the analytics. Aurora-only sub-tabs are hidden in Athena mode.

Each section answers one question, and a view that reads a different store says so: a CloudWatch panel sitting beside SQL-derived latency legs invites a reader to compare two numbers sharing neither a clock, a population, nor a refresh cadence. Deep links (`?admin=<tab>`) address the **sub-tab**, so a link resolves whichever section holds the tab.

## How quality is judged

The intent dashboard (Performance > Overview, its **Effectiveness** drill) ranks intents worst-first. Each row is one intent, and the columns are deliberately kept apart rather than blended into a score, because they fail for different reasons and have different owners.

### Three inputs, never blended

| Input | Who produced it | When | Where it shows |
|---|---|---|---|
| **Routing confidence** | the classifier, about its own decision | at the moment of classification | the *Routing confidence* column |
| **Post-hoc evaluation** | a judge model, reading the exchange afterwards | on a schedule, in batch | *Relevance* and *Task execution* |
| **User signal** | a person | whenever somebody chooses to say something | the *User signal* column |

A blended score would hide which of the three is failing, and they disagree usefully: a confidently-routed intent with good relevance and a high flag rate means the machine thinks it did well and the people using it disagree, which is the most informative state on the page.

### Routing confidence

The average confidence the intent classifier reported (high/medium/low, scored 100/50/0), plus the share of exchanges re-routed away from this intent. A low score is a **taxonomy or classifier** problem, distinct from whether the work then succeeded. This is not the conversation classification (premium/standard/basic) - that is the Tier filter.

### Relevance and task execution

**Relevance** is a judgment about a *message* and applies to every scored turn, inside a task or not. **Task execution** is a judgment about *work* and applies only to intents that open multi-step tasks; every other intent shows a dash, because it has no task execution to report and a 0% there would read as having failed every time.

Relevance carries the number of turns actually scored beside it. An average over three turns and one over three hundred read identically and mean nothing alike.

Where tasks did not complete, the cell says what happened to them - **failed** (the assistant could not finish), **left** (the person walked away), **running** (still open). A bare completion rate would collapse all three into one "not completed" bucket, and those three have different owners and different fixes.

The task statuses come from the flow evaluator's verdict over `completed | in_progress | abandoned | failed`. They are deliberately **not** the task row's own status, where `abandoned` is written only when somebody pauses a task and means *paused* - counting it would report a person who stepped out for two minutes as a person who gave up.

### User signal

The share of **rated** replies somebody marked "Needs work", with the counts beside it.

**Denominator.** It is votes cast, not replies sent. Voting is voluntary and most replies get none, so a rate over replies would read as a satisfaction score when the unrated remainder is silence, not approval. Read it as a **floor on dissatisfaction**, never as a measure of satisfaction.

Two renderings that look similar and are not:

- **a dash** - nobody rated this intent. Nothing was measured.
- **0%** - people rated it and none objected. That is a measurement.

Where a reason was given, the flags break down by axis - **wrong assistant** (routing was wrong), **poor answer** (routing was right, the answer was not), **had to re-ask**. Giving a reason is optional and the vote counts the moment it is clicked, so "no reason given" is the common case rather than a gap.

The thresholds that color this column are **untuned defaults**. A flag rate is shaped by how visible the control is and who is using the product, so the trend is readable long before the level is.

## Flagging a response

A flagged response can be raised by any of three, and the **Flagged** list names which:

- **Judge** - derived from the evaluation store (low relevance, non-compliant, or judge flags attached). Nothing is stored; re-evaluating re-derives it.
- **Moderator** - raised by hand from Oversight > Conversations. Open a conversation, and each assistant response carries a flag control in its Moderate column. Pick a reason; re-flagging replaces it, and withdrawing deletes it (an unflagged response is the *absence* of a flag, not a stored "cleared" state).
- **Person** - an end user clicking "Needs work" in the chat client.

A response raised by more than one origin appears **once**, listing every origin that raised it. Three rows for the same answer would read as three bad answers; that all three agreed is the fact worth surfacing.

Human-raised rows sort to the top. They carry no relevance score, so the score-ascending order that serves judge flags would bury every one of them - and a row nobody scored shows **not scored**, not 0.

The reviewer's verdict (approve/reject, with a note) applies to a row whatever raised it, and is stored separately from the judge's own record, so re-evaluating an exchange never silently discards a human review.

## Conversations

This is the **conversation-administration surface of the admin console** (see `docs/specs/interaction/governance/SPEC-MODERATION.md`, which describes the full open set of surfaces). Two halves, deliberately separate:

**Viewing.** It reads the ARCHIVE, not live Amazon Chime SDK. The conversation list and a conversation's messages come from the analytics archive (the system of record for history) - so you see every conversation regardless of which assistant created it. Open a conversation from the list to load its messages and members.

**Inspect a message:** click **ⓘ Info** on any message row to open a side drawer showing the stored fields - full content, the sender's **id** (the ARN, whose last segment is the sender's AppInstanceUser id, the person key every analytics table joins on) and the literal text **identity not shown** where a name would sit, because the message read carries no name for anyone; a name appears on the transcript behind it only when the identity call described under "Access" answered. Also timestamps, redacted flag, role/tier, the parsed **metadata** (model, intent, tokens, latency, …), and the raw payload (incl. `MessageAttributes`). This is the audit/debug view, and it identifies a sender by id whether or not it names one.

**Review an attachment:** if the message carries an attachment, the Info drawer shows it with an **Open attachment** button. Opening it vends short-lived, channel-scoped, **audited** S3 credentials for exactly that file and presigns the download client-side - the console never holds standing S3 access. Assistant deliverables (`generated-docs/…`) open under the `attachment-read` capability; user-uploaded files (`attachments/…`, which may hold PII) open under `attachment-read-uploads`, a moderation-grade capability whose audit line is marked `sensitive`.

**Members:** the Members panel lists current members by **id**; **add** a member by ARN (must belong to this app instance) or **remove** one (×). **Membership history** below it is a timeline of joins / leaves / moderator grants, sourced from the archive - the audit trail (Amazon Chime SDK exposes only the *current* members, not history). The service admin creates conversations and leaves once the room is assembled; in Aurora mode its own join, moderator grant and leave in the first 2 minutes are labeled "room setup by the service" and left out of the current-state view, while a later join by the same admin is shown as an ordinary join. In Aurora mode the timeline also shows subject changes: a drift flag at the time it was flagged, how it ended as a separate "Flagged subject" row at the time that was decided (kept here, moved to a new conversation, moved then rejected there, moved and unused, or offer not answered), and each subject a summary version added or dropped. The "Current state" filter keeps them. The timeline renders each member's **id**, because the membership read carries no name for anyone; the "· by *inviter*" clause is **absent** rather than blank, because the archive stores the inviter as a name with no id beside it to fall back to.

**Two reads.** The two panels read differently, and that is not a defect in either. The Members panel is read client-side straight from Amazon Chime SDK `ListChannelMemberships` under the admin bearer, on a `view-live-members` credential vended for that conversation, rather than from the admin-conversations API, so it never passes through the server-side omission and the member's name reaches the browser whatever the caller holds. It renders the id anyway, because the client is never told whether the caller holds the identity grant and cannot gate a decision it was not given - so the id here is the panel's own choice, not a control acting. The timeline below it is the archive read, where the name is not in the payload at all.

**Administer a message:**
- **Redact** blanks a message's content (recoverable concept: the message stays, content removed). A channel **moderator** can redact; so can the admin.
- **Delete** removes the message entirely. **Delete requires the app-instance admin** - a moderator cannot delete. It is **irreversible** (you'll confirm).

All admin actions run as the operator's own admin-plane AppInstanceUser, an app-instance-admin identity that the admin credential exchange creates and tags with its owner's AppInstanceUser ARN, so audit and erasure attribute it to the operator (**PARTIAL:** it is `${personId}-admin` and carries the `owner` tag; archival attributes it by its id rather than the tag), on a credential vended per action from the capability's own route (`POST /exchange-credentials/admin/<capability>`), narrowed to the one conversation and issued only with a stated reason; the dedicated **service** app-instance-admin is used only for no-human automation (e.g. membership-audit auto-revoke). What is recorded:

- **The vend**, server-side in CloudWatch: `admin_scoped_credential_vend`, with the operator, the conversation, the capability, the reason and the lifetime (`admin-credential-exchange.ts`).
- **The action**, by AWS CloudTrail: the console calls Amazon Chime SDK Messaging directly under the vended session, and the platform trail (on unless `-c platformTrail=false`) records those calls as management events.
- **Moderation record.** After a redact or delete the console posts `moderation-record`; the actor is taken from the signed request (best-effort, Aurora `moderation_actions`).
- **Client telemetry**: `admin_message_redacted`, `admin_message_deleted`, `admin_conversation_deleted`, `admin_member_added` and `admin_member_removed`, sent by the browser after the call succeeds (`adminChime.ts`). Useful for analytics; not an audit control.

**Drift Detection** (toggle in the Conversations header) lists conversations that drifted from their topic - Aurora-mode only (honest-empty banner in Athena).

## Targets

Every measurement surface shows its **target** so a number is interpretable at a glance. Metric cards show a "Target <=/>= X" line with a good / warn / bad color; the Latency view draws **target reference lines** on an actual-vs-target trend. Targets live in one place (`metricTargets.ts`, tune them there) and are sourced to published standards, not guesses: Google web-vitals, the drift-validation goal (>=95% TPR, <=5% FPR), the evaluation score bands, and for latency the industry response-time research below. A metric in **bad** (or **warn**) status is not just colored red in place - it is also collected into the consolidated **Alerts** tab (Operations section, Aurora mode), which lists every breaching metric with its value-vs-target and a link to its drill. Pushing an off-console notification (email, paging) on a breach is a separate concern the console does not do.

**Perceived latency.** Latency reads differently here, on purpose. A reply is delivered in two phases: a placeholder lands in under a second, then the answer updates it in place, because the assistant runs a multi-step tool loop (two or more model calls plus a retrieval; see [`MESSAGE-FLOW.md`](../developer/MESSAGE-FLOW.md)). So the latency a user actually perceives is **time to first feedback (TTFF, target <= 1s)**, and total time is a completion and throughput signal bounded by the Nielsen 10s attention limit, not a 2s single-hop budget. **If total latency looks "red," check TTFF first.** The full basis, the per-hop breakdown of where the time goes, and the citations are in [`LATENCY-TARGETS.md`](../developer/LATENCY-TARGETS.md).

## Reading one assistant

A classification declares **roles**, and a role has two assistants: the live assistant serving it, and an `alt` that a battle adds as a challenger. So "premium" is not one assistant once a second role is declared.

The Performance filters are where that separation lives. They cascade **classification, then assistants and roles within it, then versions**, and the choice is held in the URL, so a filtered view can be sent to somebody and opens the same way. The filtering happens in the query rather than in the browser, so a filtered number is computed over the filtered population rather than a subset of a page.

**Intent grain.** The grain is the intent, and the assistant is a filter over it. There is no per-assistant ranking table, so comparing two assistants means selecting one, reading, and selecting the other. Worth knowing before building a comparison out of two screenshots.

A role's assistant appears as its own row once it has answered a turn. For example, once an `ops` assistant on `premium` has answered, the Latency groups table carries `ops-premium` in the role `ops` with its own turn count, time-to-first-feedback and worker time, beside `advisor` in the role `primary`. If a role's turns are showing up under the primary's name, that is the attribution reading a per-function value rather than the assistant that answered, and it is a defect rather than a filter you have set wrong.

All of these surfaces are Aurora-only. In Athena mode the assistant, role and version dimensions are unsupported rather than empty, and the view says so.

## Athena vs Aurora mode

AgentEchelon runs **Athena mode** (default) or **Aurora mode** (`--context analyticsMode=aurora`). Aurora-only views (Evaluation - the intent dashboard, its drill, and the folded-in evaluations/flows/tasks/steps detail - plus Flagged, Ground Truth, an experiment's results and battles, the Alerts tab, and drift detection) are **hidden** in Athena mode; where a base view depends on Aurora-only data it shows an honest **"Aurora-only - enable Aurora mode"** banner rather than a silently empty table. Admin actions (redact/delete/members), attachment review, and profile management are **mode-independent**. So is participant-identity visibility: both the Athena read and the Aurora read drop `senderName`, `memberName`, `invitedBy` and `moderatedByName` and blank the nested name inside the raw stored payload, for every caller, so switching modes never widens who a participant's name is disclosed to. Archive-backed Conversations viewing uses the Athena archive.

## Cost sleep mode

If the deployment was deployed with `-c sleepMode=true` (Aurora mode only - see `docs/specs/foundations/SPEC-COST-SLEEP-MODE.md`), an idle instance **auto-pauses its Aurora data plane** after `sleepAfterIdle` (default 2h) to stop incurring cost, and users see a "paused" banner instead of database timeouts. As an operator:

- **Wake it:** `POST {adminApi}/query/deployment/wake` on `AdminApi` (its `AdminApiUrl` output; SigV4-signed by a role holding `manage-deployment`) restores the Aurora capacity and clears the paused state. `POST {adminApi}/query/deployment/sleep` forces sleep on demand.
- **Check state:** `GET {personApi}/deployment/state` (public, the one route on `PersonApi` with no authorizer; its `PersonApiUrl` output) returns `awake` / `asleep` - the source the frontend paused-banner reads.
- Sleep/wake events are emailed to `sleepRecipients` via SNS (delivered even while asleep). Nothing is torn down; wake is a fast, reversible capacity change.

## Admin notifications

The platform raises admin-facing alerts - Layer 6 membership-audit findings (uncleared memberships) and admin-error alerts - and delivers them into a dedicated **Admin Notifications** conversation, in-app plus email. Enable it at deploy time:

- **Turn it on:** declare `admin` in `capabilities`; the channel belongs to the `admin` capability (the `AdminServices` stack). Every core stack that raises an alert puts an `ae.alert` event on the account's default EventBridge bus, and the one rule in `AdminServices` posts each into the channel. Without `admin` there is no rule, so those alerts are **log-only** (CloudWatch) - they are not lost, but no human is paged. `membershipAuditAlertChannelArn` is retired and synth refuses it.
- **Ownership.** The channel is created and owned by the **admin assistant** (an AgentEchelon assistant, defined by a capability profile), which is also the identity that posts every alert. Its **members are the `admins` group of each issuer whose groups can be listed** (the deployment's own pool), and they are the in-app + email recipients. An administrator whose `admins` group is translated from a provider is not a member (**NOT BUILT**, [Who signs in](#who-signs-in-and-what-their-groups-give)). The service app-instance-admin identity is deliberately **never a member** - it is the cross-channel administration identity and stays out of channel rosters; the admin assistant, not the service admin, posts.
- **Adding an admin later.** Membership is synced when the channel is provisioned. A person added to the `admins` group after the last deploy is not a recipient until the channel is re-provisioned - redeploy the `<prefix>AdminServices` stack (below).
- **Repair:** from `backend/`, `npm run deploy:stack -- <prefix>AdminServices`. `<prefix>` is the instance name `AE_INSTANCE_NAME` in PascalCase (default `agent-echelon`, so `AgentEchelonAdminServices`); `npx cdk list` under the deploy context prints the exact stack names. The stack's channel resource runs on every deploy of it: it finds the recorded channel, re-syncs the `admins` roster, and publishes the channel ARN under the instance's SSM root.

Design and identity model: `docs/specs/interaction/governance/DESIGN-ADMIN-AGENT-NOTIFICATIONS.md`.
