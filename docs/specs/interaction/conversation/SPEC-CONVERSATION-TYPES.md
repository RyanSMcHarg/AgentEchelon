# SPEC: Conversation Types

**Status:** Partial. A conversation is a type rather than only a classification: the canonical creator records the resolved type key on the conversation and resolves its policy by that key, and the turn path reads the same stamp. No type key is a classification value; the shipped types are `general` (the ordinary conversation every person opens and every drift split spawns), `ops`, `ops-team`, `guest-visitor` and `customer-engagement`. Thirteen of the nineteen dimensions are consumed: `driftEnabled` at the turn, `expiration` at creation, `defaultAgents` at creation, `classifications` as a check the creator refuses against rather than a value it reads, `membershipSource` at creation and by the membership reconcile, `initiation` at synthesis, where only a type a person does not open is given an event creator, `openedBy` at synthesis, where each declared event becomes one EventBridge rule targeting that creator (FR17), `name` at creation, where a room opened for a purpose is named from what opened it (FR32), `participants` by the participant-role resolvers (FR30), `upgrade` and `seedFrom` by the guest bind and claim paths (FR24, FR26), `invitations` when an invitation is issued and redeemed (FR25), and `admitsIssuers` on every add path (FR23). `commsChannels` and `capabilities` are checked at synthesis against the deployment's declared capabilities and applied to no conversation. The other four (`messageFlow`, `connectors`, `offboardMode`, `metadataSchemaVersion`) are declared and read by nothing. The person-facing route serves a bundled function that calls the canonical creator ([ADR-053](../../../design/decisions/053-a-conversation-records-its-type-rather-than-being-pinned-to-it.md) decision 1), so a conversation a person opens carries its type's retention, its assistants and its flow. **The limit is that no client can name a type.** The person-facing API accepts no `conversationType` parameter, so the key it stamps is always `general`, whose classification is the opener's own input. `classificationAllowedForType` is unexercised on that path: vacuous while `general` declares no classification list, and load-bearing once a type can be selected. ADR-053 also settles how a type is maintained for a live conversation and recorded for an archived one, and **none of its propagation, storage or provenance decisions is built**, so a change to a type reaches conversations created afterwards and no others. Of the customer types, `guest-visitor` (the plan's `visitor`) and `customer-engagement` are registered, with the `upgrade` and `seedFrom` dimensions and the `upgradedFrom` channel tag (FR24, FR26, FR27; active only on a deployment that declares a guest issuer and the `guest` and `customer` classifications). Issuer narrowing (FR23) is a dimension, `admitsIssuers`, applied after the clearance check on every add path (**NOT VERIFIED** on a deployment; no shipped type declares a list); `deal-room` and `customer-meeting` are **NOT BUILT**. Invitations are a dimension, `invitations`, read when a member invites somebody and when the invitation is redeemed (FR25). Participant roles, which give the declared `participants` dimension its readers, are built, **NOT VERIFIED** on a deployment, for the `event`, `group` and `invitation` sources, the type's default role, a role as a member, the person whose confirmed proposal opened the conversation and the role a creating application asserts (`host`, member trust, never deciding) (FR30, FR31); the `resolveVia` source is **NOT BUILT** (FR30).

The first deny-tests the event creator's deployed role: it may stamp, read a membership and resolve assistant handles at its own classification and at no other. The second opens a conversation as a person and asserts it carries a channel flow and its type's expiration, holds the person and an assistant, and keeps no service admin as a member. `tests/e2e/a-conversation-is-named-and-assembled.spec.ts` asserts that a person-created conversation is named on its first turn, by the `UPDATE_CHANNEL` event the client receives, and that the service admin is not left a member (**NOT VERIFIED** on a deployment). `tests/e2e/a-room-an-event-opens-is-named-from-its-context.spec.ts` (phase `conversation-assembly`) asserts FR32 on the deployed typed creator: an `ops-team` room opened with no label is named from its summary, and one opened for an alarm and its service is named from the two, each at creation (**NOT VERIFIED** on a deployment). `tests/e2e/an-agent-step-addressed-to-a-role-reaches-only-its-holders.spec.ts` (phase `welcome-workflows`, gated by `WELCOME_WORKFLOWS_E2E=1`) asserts FR30's role audience for an `agent` step: in an `ops` room, the step addressed to `{ participantRole: lead }` posts one `event_step` message targeted at the lead alone, and a member who holds no role receives nothing of it. **Site section:** Interaction layer, conversation.

---

## Overview

**A conversation is a configurable experience rather than a fixed chat, and the conversation type is where that configuration lives.** A support case, a sales engagement, a scheduled service visit and an alert-triggered incident room are all "a conversation", and each needs different participants, a different assistant, different transports, different access and a different relationship to the business's systems of record. The type is the **composition root**: one named bundle that says which assistant, which access, which external systems and which capabilities an experience gets.

**Handlers read dimension fields; nothing switches on the type.** That is the property the whole pillar exists to protect. A new experience recombines dimensions that already exist, and a genuinely new behavior is a new dimension added once, so the catalog of experiences can grow without a second code path for each entry.

**A type carries a classification and never is one.** `classification` is the only closed axis IAM evaluates, and a classification is a declared set of grants rather than a ladder ([ADR-046](../../../design/decisions/046-classifications-are-a-set-not-a-ladder.md)): it reaches exactly what its `grants` declare, and an undeclared set is an unknown classification that reaches nothing. Conversation types are meant to proliferate and need no relation to one another at all - there is nothing to compare between a support case and an engagement. So the type names one of the deployment's classifications, and **adding a type never adds a classification**, which keeps the deny-tested security axis minimal while the catalog stays open.

**The conversation is the hub every transport and connector attaches to.** A non-chat transport and an external system post their artifacts back into the conversation and link their own records by reference, so "the history is attached to the conversation" needs no second aggregate store: the channel is the conversation.

**The person never sees any of this, which is the point.** What they see is a conversation that opened the right way, with the right people and the right assistant in it. The type is the reason that happens without a deployment forking the handler code.

## Business Problem

A business that wants to run several kinds of conversation on one platform has to choose today between writing a new handler, or a whole separate application, for each one. Both cost the same thing twice: the team that owns the support flow and the team that owns the incident room each maintain their own copy of routing, access, delivery and history, and the two drift. What the business actually wants is to stand up a new experience by describing it - these participants, this assistant, these transports, this classification, these external systems - and have the platform run it. Without that, the platform's reach is capped at the experiences somebody has already written code for, and every new one arrives as a project rather than as a configuration change.

## Personas

Personas are defined in [PERSONAS.md](../../../overview/PERSONAS.md) and are not redefined here. This pillar is written for the two personas who compose an experience, and is experienced by a third who never reads it.

### AI developer

**How this relates to them:** they own the assistants a type selects, and the type is where their assistant is attached to an experience. Their question is whether they can add or tailor an experience without touching the code that serves every other one.

**Goal:** stand up or tailor an experience by editing a registry entry, with the code that serves every other experience untouched.

| What they need | Requirement |
|---|---|
| A new experience as a registry entry rather than a new handler | FR5, FR6 |
| Name the assistants an experience uses | FR6 |
| Declare which external systems the experience may reach, and for what | FR11 |
| Decide how this experience opens, given what orients it | FR10 |
| Declare the participant roles people hold in an experience, where each is resolved from, and what each confers in the room | FR30, FR31 |

### Admin / operator

**How this relates to them:** they run the deployment and answer for what it retains, what it costs and what it is allowed to reach. Every dimension below is policy, so every one of them is something they can be asked about in an audit.

**Goal:** answer for what each kind of conversation retains, reaches and admits, with no type able to widen access.

| What they need | Requirement |
|---|---|
| A type that names its classification, with no way for a type to widen access | FR1, FR2 |
| Retention set per experience rather than per deployment | FR4 |
| A live conversation that takes a configuration change and still says which configuration it ran under | FR13 |
| A misconfiguration that degrades safely instead of failing a conversation | FR2, FR14 |
| Topic-drift suggestion on or off per experience | FR3 |
| A team room whose people are exactly a directory group, kept in sync without manual invites | FR17, FR18 |

### End user

**How this relates to them:** they never see the type. They see a conversation that already has the right assistant in it, opens with copy that fits what it is for, and holds the history of the work rather than of the transport it arrived on.

**Goal:** a conversation that opens ready for what it is for, with the right people and assistant already in it.

| What they need | Requirement |
|---|---|
| A conversation shaped to the moment rather than one generic chat | FR5, FR6 |
| An opening that orients them to this particular conversation | FR10 |
| One history, whatever transport the work arrived on | FR8, FR11 |
| A departed member who still reads correctly in the history | FR12 |

## Functional Requirements and Acceptance Criteria

**Priority is a keep-or-cut decision set against what the field expects, not against how interesting the work is.** `Table stakes` means a deployment without it is behind. `Differentiator` is worth the cost because few platforms do it. `Gap - prioritize` marks a requirement whose absence puts this below comparable systems. `Above bar - optional` is more than the field asks and can wait. `Optional - attach instead` should be bought rather than built. `Enabler` is not user-visible and is what makes another row affordable.

**Delivered distinguishes a field that is declared from a field that is read.** A dimension in the schema that nothing consumes at the turn is not a feature a deployment can use, and saying otherwise is the specific way this document could mislead.

### A conversation opened by an event, with two assistants in it

The worked case is an operations conversation: something happens in the deployment, and instead of a person noticing, a conversation opens with the classification's primary assistant and its `ops`-role assistant both enrolled, linked to the conversation the event concerned. It is the shape that makes several of the dimensions above worth reading, which is why it is recorded here rather than as a separate document.

**What is built.** The `ops` type declares `premium` as the one classification it permits, drift off, thirty days of `expiration` rather than `general`'s 270, its people from the `ops` group, and a roster of two assistants. `typed-conversation-from-event` opens a conversation of that type: it resolves each declared handle through the live assignment records, adds both assistants, adds the admitted members of the `ops` group (FR18) and never the concerned conversation's roster, applies the type's own `expiration`, records the type key where the turn path reads it, records the concerned conversation as its parent (`parentChannelArn`, FR27 records that the tag form is not built), and writes nothing into the concerned room (FR17). The classification is the function's deployed one and is checked three times - the type must permit it, the concerned conversation must already carry it, and the role's `chime:TagResource` is conditioned on `aws:RequestTag/classification` so no other value can be stamped.

**How the roster is built.** The service admin creates the channel so the flow attaches before any assistant; the primary is then added and made moderator. The person, the rest of the room and the type's assistants are added with the service admin as bearer, because it has been a moderator since `CreateChannel`. The service admin then drops its moderator record and its membership in a `finally` (`createConversationCore`, `channel-creation.ts`), so a creation that fails partway still removes it; each step is best effort and logged loudly when it fails. A host's context conversation (`createConversationForContext`) goes through the same creator, as the service admin. With no service admin configured, creation is refused rather than made as an assistant. Each assistant the type names is added once: the type names `advisor`, which on a premium deployment is also the classification's primary, so the creator skips an assistant that is already a member rather than adding it twice. An unknown type key and an event naming a conversation at another classification are both refused.

**Verified by:** `an-ops-conversation-is-its-type-and-not-its-classification` (unit: the `premium` tag, the type's own retention rather than `general`'s, the stamped key, the flow associated before any membership, the primary added once although the type names it and the second assistant added, the creation failed when an assistant cannot be added, nothing posted by the creator into the concerned conversation, an unregistered type refused), `an-event-opened-conversation-adds-people-as-its-type-declares` (unit: the `ops` group's admitted members added, the concerned roster never read), `a-typed-conversation-posts-nothing-into-the-concerned-room` (unit: no message, no notice and no membership read on the concerned conversation; a concerned room at another classification refused), `tests/e2e/a-typed-conversation-creator-creates-at-one-classification.spec.ts` (the deployed role may stamp and resolve assistant handles at its own classification and at no other, and reads no conversation's membership), and `tests/e2e/a-person-opened-conversation-goes-through-the-canonical-creator.spec.ts` (a person-opened conversation carries a flow and its type's expiration, holds the person and an assistant, and keeps no service admin).

**How an event reaches it.** The type declares the events that open it (`openedBy`), and the premium stack builds one EventBridge rule per declaration whose target is this creator, handed the declaration's id and the event; `ops` is opened by `ae.ops` / `Incident opened` on the default bus (`backend/scripts/send-ops-event.mjs`). A direct invoke still works. Once the room exists, the person the event named and the `ops` group's admitted members are welcomed into it by its primary and emailed a link into it (FR17). Verified by `event-opened-conversation-rules` (synth) and `an-event-opened-conversation-welcomes-its-people-by-email` (unit); built and not yet deployed.

**What is not.** `messageFlow` is not read: the flow ARN comes from one unkeyed parameter, and the creator refuses a conversation with no flow rather than selecting among several. The second assistant exists only where the deployment declares it (`ops-premium` in `profiles`), and without it creation is refused.

**The constraint that decides whether any of it works.** An assistant may act only in its own classification's channels, matched on the channel's `classification` tag against a wildcard resource. So an event-created conversation must carry the right tag inside the `CreateChannel` call, at which point both assistants are permitted with no IAM change at all - and if the tag is absent or wrong, both are denied silently at their first read rather than failing loudly.

**Why one creator owns creation.** Five implementations issue `CreateChannel`, and four of them create a conversation. A type means something only where one creator owns creation and reads the type, so the type is read by the canonical creator (`backend/lambda/src/lib/channel-creation.ts`), which serves the person-facing path (every conversation an ordinary person opens), the drift path and the event path. The three that remain outside are the context request of `create-conversation-at-classification.ts`, a host's add (`membershipHandler` in `conversation-management.ts`) and `proactive-briefing`, each of which resolves its own flow parameter and adds its own members; `admin-notification-channel-provision` is provisioned infrastructure rather than a conversation and is out of scope. **The gap between "the `ops` type works" and "conversation types work" is that no client can name a type, and that eight dimensions are read by nothing.**

**OPEN:** which principal re-applies a changed `applied` dimension, a question [ADR-053](../../../design/decisions/053-a-conversation-records-its-type-rather-than-being-pinned-to-it.md) leaves open beside the snapshot question it settles. One worker across every classification is cheap and takes the write outside the classification condition; one per classification keeps the boundary and costs N. A membership source drawn from a Cognito group is reconciled on the group change (CloudTrail to EventBridge) with a daily backstop sweep (FR18); an external identity provider that emits no such event relies on the backstop alone.

**OPEN:** whether `provideComms` transports post a summary or a structured card back into the conversation, and who decides. The rule that artifacts attach to the hub is settled; the shape of the artifact is not, and it is the difference between a readable history and a log.

**The upgrade follows the type's path.** A visitor who registers does not join the guest conversation's audience to their account: under path B the canonical creator opens a `customer-engagement` conversation for the account's AppInstanceUser, seeded with a summary of the guest conversation that the customer can read, tagged with the guest channel's ARN, and the guest conversation ends. Each invitation names the meeting conversation's channel ARN, the issuing AppInstanceUser and the invitee's AppInstanceUser; an invitee who is not yet known is assigned an AppInstanceUser by the credential exchange when the invitation is made, at the latest when the meeting conversation is created, with no `Identities` row until redemption binds one. A pending invitee is created with an expiration, at its invitation's own, which a sign-in redemption removes (**OPEN (O13)** until probed live). The invitation lifecycle for an ordinary conversation is built ([SPEC-CREDENTIAL-EXCHANGE.md](../governance/SPEC-CREDENTIAL-EXCHANGE.md) §4c); for a meeting it is owned by [SPEC-ASSISTANT-MEETINGS.md](../assistants/SPEC-ASSISTANT-MEETINGS.md) and **NOT BUILT**.

**The incident never writes into the customer's room.** The `ops` conversation reads the customer's conversation under its declared read grant, which carries no `SendChannelMessage`, and the event path posts nothing there (FR17). A person posts any customer update.

**Customers are separated by membership, not by classification.** Every customer's conversations are at `customer`, so classification does not separate one customer from another; membership, which Amazon Chime SDK Messaging enforces per channel against the caller's own bearer, does, and retrieval over a customer conversation's content is scoped to that conversation ([ADR-008](../../../design/decisions/008-embedding-cost-and-ttl-policy.md), amended).

## Non-Goals - Out of Scope

| Out of scope | Why | Where it is covered instead |
|---|---|---|
| **Adding a classification** | A classification is the one axis IAM evaluates, so adding one touches the allow-list and its deny-tests and is a security-reviewed change. A type catalog that could add one would move that review into a configuration file | [SPEC-CONVERSATION-SECURITY.md](../governance/SPEC-CONVERSATION-SECURITY.md), [ADR-046](../../../design/decisions/046-classifications-are-a-set-not-a-ladder.md) |
| **Ordering conversation types** | There is no relation between a support case and an engagement, and inventing one would put a comparison into a catalog designed to grow. Only the classification a type carries is compared, and that comparison is IAM's | FR1, [SPEC-CONVERSATION-SECURITY.md](../governance/SPEC-CONVERSATION-SECURITY.md) |
| **Reimplementing a vendor's routing or assignment** | The business already decides who owns a case. A connector resolves the participant through the vendor's own router and the platform admits them | [SPEC-CONNECTORS.md](../../communication/SPEC-CONNECTORS.md) |
| **Duplicating a system of record** | Reading each source live is the commitment (tenet P5). A copy is a second thing to be stale and a second thing to secure | [SPEC-CONNECTORS.md](../../communication/SPEC-CONNECTORS.md) |
| **A per-type handler, or a switch on the vendor** | The moment either exists, adding an experience stops being configuration, which is the whole claim of this pillar | FR5, [SPEC-INTERACTION-LAYER.md](../SPEC-INTERACTION-LAYER.md) (the platform invariants) |
| **A separate aggregate store for conversation history** | The channel is the conversation, and every transport and connector attaches to it. A second store would need reconciling with the one that already holds the events (tenet D7) | FR8, [SPEC-CONVERSATION-ARCHIVE-AND-MEMBERSHIP.md](./SPEC-CONVERSATION-ARCHIVE-AND-MEMBERSHIP.md) |
| **Breaking changes to the schema** | A deployed conversation must keep working across an upgrade, so the schema is additive and deprecations are soft | FR13, FR14, [SPEC-INTERACTION-LAYER.md](../SPEC-INTERACTION-LAYER.md) (forward-compatible by contract) |
| **A client that defines type policy** | Policy resolved in a browser is policy a browser can change | FR15, [SPEC-CHAT-APP.md](../../interface/SPEC-CHAT-APP.md) |

## User Experience Description and Mocks

The conversation type has no surface. It is experienced as the difference between two conversations that would otherwise be identical, so the journeys below are written as what a person meets rather than as what an operator sets.

### The tiered private chat, which is what ships

1. **Somebody opens a conversation and picks a tier.** That tier is the conversation's classification. Its type is `general`, which takes the classification as its input (FR2).
2. **The conversation opens with this deployment's own orientation** (FR10). Nothing about the opening is type-specific yet, which is exactly what the defaults guarantee: an unconfigured type is unchanged.
3. **The assistant for that classification is in the room**, because the classification's own configuration put it there rather than the type naming it (FR6).
4. **Drift suggestion is on**, so a conversation that wanders is offered a new one (FR3).
5. **The conversation expires** on `general`'s `expiration`, 270 days after its last message, applied by the canonical creator from the conversation's own type (FR4).

### The experiences the model is built for

Each is one registry entry plus, where a non-chat transport or an external system is involved, a connector. None requires a handler change, and each is illustrative rather than shipped.

| Experience | Shape | What it needs beyond today |
|---|---|---|
| Engagement | A single assigned owner by default, not exclusive, with reassignment as a membership operation | The participant policy read at admission (FR9's sibling, FR7) |
| Support | A widget or a phone call reaches assistant triage, and the vendor's router resolves the agent for the case | A transport connector and participant resolution (FR7, FR11) |
| Service | A scheduled visit, masked voice and messaging, a meeting, one attached history | Initiation by schedule, a comms connector, artifacts back into the hub (FR8, FR11) |
| Internal IT | In-context help becomes a routed service-desk ticket, which is the smallest first connector | One connector implementing the record sync (FR11) |
| Incident triage | An alert opens the room, the on-call dials in, live data is read in, a vendor is escalated to | Initiation by alert, the generated welcome over incident state, and a fetch-context connector (FR7, FR10, FR11) |

The incident room is the case that justifies the generated welcome: no template can summarize state it has never seen, so a type carrying arbitrary state needs the assistant to fill the shape in, and the deterministic mode is what it falls back to when the model is unavailable or misses the deadline.

**Mocks.** None. There is nothing to draw: the type is policy, and its whole visible effect is the conversation the other web-client documents describe.

## Appendix A - The shipped schema

The registry lives at `backend/lib/config/conversation-types.ts`, and the connector shapes at `backend/lib/config/connectors.ts`. The type **key** is the key of the map an entry is stored under rather than a field on the entry, so a deployment adds a type by adding an entry.

| Field | Shape | Consumed today, and where |
|---|---|---|
| `classifications` | The classifications a conversation of this type may carry; absent means any conversational classification. The only closed axis IAM evaluates is the classification itself, an input at creation | Yes, as a CHECK rather than as a value. `classificationAllowedForType` compares it against the classification the creator was given, and an event-initiated creation is refused when they disagree; an unknown type key permits nothing rather than falling back. Every path stamps the tag from the classification its caller supplied, and no path reads this field as that value |
| `driftEnabled` | Boolean, its own top-level field because it shipped first | Yes |
| `expiration` | A number of days plus the criterion it counts from, deleting the whole conversation. A MAXIMUM, bounded above by `MAX_CONVERSATION_TTL_DAYS` (270). Separate from `MESSAGE_RETENTION_DAYS` (90), the app-instance-wide Amazon Chime SDK retention that prunes messages | Yes, at creation: the canonical creator writes the type's value onto the channel on the primary, drift and event-initiated paths (`general`: 270 days from the last message; `ops`: 30), and a person-facing request may ask for a shorter life; a host's context conversation takes `general`'s; the briefing path sets none. Nothing re-applies it afterwards (FR19) |
| `initiation` | Who or what starts a conversation of this type. Default is a person | At synthesis only - a classification's stack builds the event creator only for a type whose initiation is not a person and which permits that classification. At the turn, no |
| `openedBy` | The events that open a conversation of this type: per entry an EventBridge `source`, `detailType`, optional `detail` filter and bus, whether it matches this deployment's instance, the classification its rule is built at when the type permits several, and per creator field (person, label, summary, concerned conversation, the alarm the room watches, and the service the event is about, read for the room's name alone) a path into the event or a fixed value. Never a classification or a type | Yes - at synthesis, where each entry becomes one rule on the stack of the classification it resolves to and an invalid entry fails the synth, and by the event creator, which reads the declaration a rule names (FR17) |
| `name` | The name a conversation of this type is created with, as a template over what opened it (`{{label}}`, `{{summary}}`, `{{alarm}}`, `{{service}}`, `{{date}}`), in the builder's own words. A template that inserts a field the opening does not carry is passed over. Absent: the platform's default for the kind of room (FR32) | Yes - at creation, by the typed creator and the classification's creator (`conversation-name.ts`); a field outside the five is named by `conversationNameErrors` |
| `membershipSource` | Where a conversation's people come from, enforced: an identity-provider `group`, a `list` of subjects, or both. Absent is manual | Yes - at creation (the admitted set is added, and the source is stamped on the conversation) and by the per-classification membership reconcile, on each group change and on a daily backstop |
| `defaultAgents` | The assistants the experience enrolls, by HANDLE rather than by bot ARN - the ARN is minted per deployment | Partly - the event-initiated path resolves each handle through the live assignment records for the conversation's classification and adds them, failing the creation when one cannot be added or resolved. No other path reads it |
| `messageFlow` | Which message flow routes the conversation - `@assistant` and `@all` addressing, marker stripping, the placeholder correlation map. A key the deployment resolves to a channel-flow ARN, never an ARN in config | No - every shipped type names the default flow and `resolveMessageFlowKey` returns it, and no creator reads the resolved value. One unkeyed parameter publishes one flow ARN, so there is nothing to select among; the event-initiated path refuses a conversation with no flow, which is a floor rather than a selection |
| `commsChannels` | Chat plus any non-chat transport. Chat is the default and the hub | At synthesis only - resolved against the declared capability list, with each gap recorded (FR7, FR14) |
| `capabilities` | An open bag of feature switches beyond drift | At synthesis only - resolved against the declared capability list, with each gap recorded (FR9, FR14) |
| `participants` | Who joins, who may be pulled in, and which connectors resolve a role to an identity; its `participantRoles` and `defaultRole` (FR30, FR31, DESIGN-CONVERSATION-TYPES section 6.1) declare each participant role's sources and what it confers | Yes, for `participantRoles` and `defaultRole`: read by synthesis, the canonical creator, the invitations path, the ADR-060 resolver and ADR-061's event workflows (FR30). The membership reconcile reads none of it (**NOT BUILT**), and `seed`, `mayAdmit` and `resolveVia` are declared and read by nothing |
| `welcome` | The mode, the copy shape, and the context sources that orient the opening | No - removed from the type. Retired by [ADR-061](../../../design/decisions/061-a-welcome-is-a-workflow-an-event-starts.md) decision 9 rather than wired: the welcome is the assistant's version's workflow, selected by the type it names in its `types`, and is not declared on the type |
| `invitations` | The redemption modes a type's invitations admit (`sign-in`, `link`), its default, the `linkClassifications` a `link` invitation may be redeemed at, and how many days an invitation lasts. Absent, nobody is invited into it; a type with a membership source declares none | Yes - by the invitations function when a member invites somebody, by the credential exchange when a `link` invitation is redeemed, and at synthesis, which refuses a type whose link classifications shares no classification with the `invitation-link` issuer (FR25) |
| `admitsIssuers` | The registry ids of the issuers a conversation of this type admits; absent admits every issuer the classification admits. A narrowing, never a grant (FR23) | Yes - after the clearance check on every add path (FR23), and at synthesis, which refuses a list naming no declared issuer |
| `connectors` | Which external systems the experience may reach, and for which capabilities | No - the connector registry is built (`backend/lib/config/connectors.ts`, SPEC-CONNECTORS), and nothing reads a type's `connectors` list yet |
| `offboardMode` | How a departed member appears in the history | No |
| `metadataSchemaVersion` | The forward-compatibility snapshot version | No - nothing writes or reads it |
| The TYPE KEY itself | Not a field: the key of the map entry. Recorded on a conversation at creation in the server-side channel-context store, never in channel Metadata - Metadata is member-writable, so a type stamped there would let a member choose their own conversation's policy | Yes - the drift gate resolves the type from it where the stamped type is registered and to `general` otherwise; the classification is never used to choose a type, and a missing stamp or one naming a classification (`basic`, `standard`, `premium`) resolves to `general`. It is a mutable, last-write-wins read path and NOT provenance; the durable record is ADR-053 decision 7, which is **NOT BUILT** |

**Proposed dimensions, NOT BUILT.** The customer types add four, each read at creation or admission and none a grant: `admitsIssuers`, the issuers a type narrows admission to (FR23, built as described there); `guest`, whether a guest may open it, with `upgradePath`, `A` or `B` (FR24); and `seedFrom`, the type keys a conversation of this type may be seeded from (FR26). A link to another conversation is not a dimension: it is a tag the creator writes on the channel (FR27).

Three entries ship, and none is named after a classification (`conversation-type-keys-are-not-classifications.test.ts` fails if one is). `general` is the ordinary conversation: it declares no classification list, so the opener's own classification is its input, keeps drift on, has manual membership, and retains for the platform maximum from the last message. It is the default type, and a conversation with no stamp or a stamp naming a classification (`basic`, `standard`, `premium`) resolves to it, with no migration. `ops` permits `premium`, turns drift off, declares thirty days, takes its people from the `ops` group, and names two assistants. `ops-team` is the operations group's standing conversation: opened by the platform (`initiation: 'system'`) with no conversation concerned, `premium` only, its people from the same group, drift on, and Advisor added.

**Connector capabilities**, declared and not yet implemented by any registered vendor: resolve a participant, sync a record, fetch context, provide a non-chat transport, and ingest an inbound event. A record sync rides a vendor-neutral event on an event bus and is idempotent by event id; ingest is its inbound mirror and is signature-verified. Externally resolved humans are admitted at the conversation's classification, so a connector feeds admission and never bypasses it. The owning contract for all of it, including per-tenant credential isolation and governed tool access as the intended vehicle, is [SPEC-CONNECTORS.md](../../communication/SPEC-CONNECTORS.md).

## Appendix B - The sections source comments cite by number

The two configuration modules cite this document by section number, so those numbers stay as the headings below.

### 5. How a type composes with the other pillars

The type is the composition root and the conversation is where it all meets. Each dimension has a safe default when it is absent, which is what makes an unconfigured type behave exactly as it does today.

| Composes with | Through | What the other pillar then does |
|---|---|---|
| Identity and access | `classification` | The conversation's classification is supplied at creation and stamped as its immutable tag; the type declares which classifications it may be used at, and the creator refuses the rest. The credential exchange enforces the tag in IAM. A participant's effective capability is what their own clearance grants and what this type's policy allows, which is two enforcement layers rather than one |
| Assistant configuration | `defaultAgents` | Selects which assistants - model, instructions, tools, guardrail - the experience uses |
| Connectors | `connectors` | Declares which external systems the experience may reach, and for which capabilities |
| Auditing and retention | `expiration` | Becomes the conversation's expiration setting at creation: through the canonical creator on the primary, drift and event-initiated paths, and from `general` on the federated path |

### 7. What must stay true as the catalog grows

- **`classification` is the only closed axis IAM evaluates.** Everything else in the bundle is open string-keyed configuration, and a classification is a declared set of grants rather than a ladder.
- **A live conversation RECORDS the policy it ran under.** A registry edit reaches conversations that are already running, because a renamed group must resolve and a shortened retention is meant for the data that already exists; what must never be lost is the ability to say which configuration was in force when, which is an append-only archived record rather than a frozen copy (FR13, ADR-053 decisions 2 and 7).
- **Resolution is lenient.** An unknown type, field or connector resolves to a safe default or is skipped and recorded, never failing a conversation, and a newer or older schema both resolve.
- **Nothing switches on the type or on a vendor, and the schema is additive only.** Deprecations are soft and the schema version is bumped rather than reused, so growth never breaks a deployed conversation.
- **Policy is backend-owned.** The client displays what it is told and defines none of it.
