## Overview

**`classification` is the only closed axis this exchange evaluates, and it is carried by which role was assumed rather than by anything the caller says.** The exchange resolves the caller's clearance through the clearance source their issuer declares (their groups, translated into AgentEchelon groups, a claim mapping, a fixed set or the one-conversation session, each within the issuer's classifications), selects the matching classification role, and the classification is a deploy-time constant baked into that role's policy. A client cannot forge it because a client never asserts it, and the axis is a declared grant set rather than a ladder (ADR-046), so reach is `grantsFor` and not "everything below me".

**Identity is bearer-pinned, so an actor can only ever act as itself.** Amazon Chime SDK does not bind `x-amz-chime-bearer` to the caller; AWS documents the opposite, that the IAM policy's bearer resource is what decides which identity a credential may act as, and widening it to `.../user/*` is the documented way to let a back-end service act as anybody. So the bearer resource is the whole of the impersonation control. A person's classification role names `.../user/${aws:PrincipalTag/person}`; an assistant's acting role names `.../bot/${aws:PrincipalTag/bot}`. The same construction, twice, because an `AppInstanceBot` and an `AppInstanceUser` are principals of the same kind on the same control plane.

**A permissions boundary is the limit, and a narrowed grant is what delegation means.** Each classification publishes one boundary managed policy on its assistant acting role, written as an allow-list of the services a turn uses plus Denies that hold whatever the role's identity policies grow to hold; raising it is a deploy. On the person side the equivalent boundary is the classification role, and an STS session policy narrows it per request. A session policy can only ever narrow, which is what makes it safe to take the requested capability set and channel scope from the request body: a forged value can only reduce access. The assistant equivalent, a session policy derived from the assistant's own approved definition, is built (§4a); guardrails and context sources other than `company-docs` are not narrowed per assistant.

**Every sensitive operation carries at least two enforcement layers.** Moderation needs the admin plane *and* a `channelArn` *and* an `AppInstanceAdmin` identity the chat role never holds. An assistant's turn is bounded by the classification tag on the channel *and* by the bearer resource on its role *and* by the order in which the session is assumed. Identity comes from validated claims *and* is pinned in IAM, so an IDOR attempt and a client bug fail at different layers.

**A membership vend is scoped to the channel and the caller, and that is all the scoping available.** The Service Authorization Reference lists `app-instance-user` and `app-instance-bot` among the required resource types for `CreateChannelMembership` and `DeleteChannelMembership`, and this repository's own server-side grants name `user/*` beside `channel/*`, so a policy naming the target looks necessary and a policy denying one looks possible. The live deny-test shows neither is true for authorization: the channel is what is evaluated. The membership vend therefore names the channel and the caller's own bearer ARN and no `user/*` resource, because that grant would add reach without adding enforcement.

**Membership stays on the admin plane, and that is a boundary rather than a preference.** The membership verbs are granted to the admin-plane role only (`MODERATION_ACTIONS` in `admin-services-stack.ts`), and a session policy only narrows a role, so vending them on the chat plane would return a credential the service refuses at use - a success that does not work, which is worse than the refusal. **OPEN:** whether a member holding moderator status should be able to change membership from the web client. It is defensible, since Amazon Chime SDK is the authority on who moderates and the channel scope bounds the reach, and it would also make the moderator role grantable after a conversation is created. It is not a change to this handler: it widens the end-user role boundary and contradicts FR15, so it needs its own decision.

**The target of a membership call is not gateable in IAM, and the membership audit is what answers that.** Amazon Chime SDK authorizes these calls on the CHANNEL: `memberArn` travels as a request parameter, so no policy can refuse one member and admit another. A Deny on every bot ARN does not hold: measured with that Deny in force, a vended `manage-membership` credential removes the assistant and promotes it to moderator, while the same credential is correctly refused an action outside its capabilities, and the IAM simulator returns `explicitDeny` for that policy on the bot ARN, so the statement is well-formed and simply never consulted. The vend carries no such Deny, and `deny-test-assistant-membership.mjs` measures the shape that holds. **This is why Layer 6 exists.** For every other axis - who holds the capability, which channel, which classification - IAM refuses before the request runs, and the audit is a backstop. For the target axis there is no policy-time check to back up, so detection and revocation ARE the enforcement (tenet D6: a reconciliation sweep is correct design where no event- or policy-time mechanism is available). **OPEN:** narrowing the vend so the handler route is the only way in would convert that detection into a refusal.

**Isolation is provable by deny-test rather than by code review.** `backend/scripts/deny-test-credential-exchange.mjs` provisions a real channel and shows the same send allowed bearing the caller's own ARN and `AccessDenied` bearing another person's - only the bearer differs, so it isolates the pin from the tag gate. `backend/scripts/deny-test-session-classification.mjs` reads the `sts:TagSession` trust condition off the deployed roles, then assumes a scratch role carrying the identical condition with a matching, a mismatched and an absent classification assertion. A synth test asserts the policy CDK emits, so a widened boundary fails the build before a deploy.

## Business Problem

A business wants every actor in a conversation - a classified user, an external person from another identity provider, a guest, the assistant - to act at exactly their capability and only as themselves, whatever identity provider it plugs in, without writing and trusting access-control logic in the frontend or once per integration. The alternative is scattering that logic across the client and each identity-provider wiring, or trusting a product that cannot enforce it below the application layer. Operators want one credential chokepoint to reason about and to revoke at, rather than access spread across the frontend and the identity provider. And a business that has to prove its access model to an auditor needs the boundary to be an AWS primitive, because "the application checks it" is a claim and an IAM denial is evidence.

## Personas

Personas are defined in [PERSONAS.md](../../../overview/PERSONAS.md) and are not redefined here. Everyone reaches the platform through this exchange, so most personas meet it as the thing that decides what their session can do; two own it.

### Platform developer

**How this relates to them:** they answer for whether an actor can ever act as another actor, so the bearer pin, the trust policies and the ordering property are theirs, and so is the honest account of where the assistant half is narrower than the person half.

| What they need | Requirement |
|---|---|
| One chokepoint for credentials, with no second path around it | FR9 |
| A pin that resolves only for a session the exchange tagged, so an un-tagged credential bears nothing | FR2, FR13 |
| An assistant that can bear only its own identity | FR10 |
| An identity fixed from a validated source before the model runs | FR11 |
| No escalation path out of a vended session | FR13 |

### Admin / operator

**How this relates to them:** they hold the only authority that crosses conversations, and the design deliberately makes that authority expensive to hold: a separate identity, one channel, short-lived, audited every time.

| What they need | Requirement |
|---|---|
| Administration on a separate identity from their own chat identity | FR5 |
| Every privileged vend recorded, naming the identity, channel, capabilities and TTL | FR6 |
| An attachment read that is hard-bound to one channel for its lifetime | FR8 |
| Reading a customer's stored message content short-lived rather than from a standing role | FR7 |
| A definite owner and effect for every lifecycle transition, including an immediate downgrade | FR14 |

### End user

**How this relates to them:** they never see the exchange, and the guarantee it gives them is negative: nobody, including a bug in the client they are using, can act as them.

| What they need | Requirement |
|---|---|
| Credentials that are theirs alone and cannot name another identity | FR2 |
| A capability boundary a client cannot talk its way past | FR4, FR15 |
| An identity derived from their verified token, never from a request body | FR1 |
| A departure that leaves their history readable rather than blank | FR14 |

### AI developer

**How this relates to them:** the assistants they build run on these credentials, so what an assistant can be asked to do, and what it can be tricked into doing, is decided here rather than in a prompt.

| What they need | Requirement |
|---|---|
| An assistant identity that is the assistant's own, never a user's | FR10 |
| An identity that no model output can change, because it is fixed before the model runs | FR11 |
| An identity whose whole lifecycle belongs to the platform, so a stale principal is not left valid forever | FR12 |
| A name that identifies the assistant across analytics, SSM and a portable profile | FR12 |

### Manager

**How this relates to them:** their use cases put external people in rooms with internal ones, so the guest and federated roles are what bound the external half.

| What they need | Requirement |
|---|---|
| An external participant bound to the conversation's classification and scoped to that one conversation | FR3, FR4 |
| A guest whose access level is deliberately minimal | FR3 |
| Per-tenant credential isolation for connector-resolved externals | FR3 |

**Also served, and not a persona in `PERSONAS.md`:** the **assistant**, a system actor that holds credentials of its own (FR10, FR11), and the **service app-instance-admin**, a non-human automation identity for no-human paths ([SPEC-ADMIN-IDENTITY](./SPEC-ADMIN-IDENTITY.md)).

**Display name owner.** This document is where the owner of a display name is stated, so a reader asking "should the client resolve names from Cognito" finds the answer here (no) rather than building a second path to the same fact.

Three parts make it hold, and the third is what makes it a security property rather than a convention: the exchange takes the name from the **token** rather than from `AdminGetUser`, because the token is the one source every IdP provides (the pool read the exchange makes at a vend asks only whether the account may sign in, §4b); only a real `name` claim triggers a refresh, so a fallback never overwrites an administratively set name; and the vended session policy carries no `chime:UpdateAppInstanceUser` while `name` is excluded from the pool client's writable attributes, so a member cannot take another member's name.

**Reading the "Validated by" column.** A **deny-test** is the strongest evidence in this repository and is called out where one exists: it runs against a deployed stack and lets IAM decide, rather than asserting what the code intends. Live deny-tests are `backend/scripts/deny-test-*.mjs`. Unit tests live in `backend/test/`; end-to-end specs live in `tests/e2e/` and are listed against their phase in [e2e-coverage-matrix.md](../../../reference/e2e-coverage-matrix.md). The status in brackets is what the test does:

- **behavior** - executes the code path and asserts on the result.
- **synthesized policy** - asserts the IAM document CDK emits, so a widened boundary fails the build before a deploy.
- **source text** - asserts that a convention still appears in the source.
- **none** - no test exists.

**Known limits on the delivered rows.** FR10's remainder is the roles named in its row. The router and the roles that create conversations and add their members hold a classification-conditioned `/bot/*` bearer on their own roles for reads, creation and membership, and post nothing on it; the channel flow's reads are unconditioned across the app instance. FR16's carrier decides which assistant a turn acts as; whether the router chose the right assistant within the classification is code, as it is for a person at the exchange. FR12's `RETAIN` exception is deliberate and narrow: the invariant that a provisioner deletes what it created holds for the classification and alt bots and not for the admin assistant's.

| Out of scope | Why | Where it is covered instead |
|---|---|---|
| An Identity-Pool path to Amazon Chime SDK as a fallback | Removed: the deployment creates no Identity Pool, so no credential exists outside the exchange. The bearer pin resolves `${aws:PrincipalTag/person}` from a session tag only this exchange sets, so a credential from any other source could not satisfy it either | FR9. `VITE_PERSON_API_URL` is required |
| Access-control logic in the frontend | A client-side check is not an enforcement layer, and a product whose isolation lives above the application cannot prove it | FR2 and FR4. The decision is an IAM evaluation before the request runs |
| Moderation on a chat credential, including an admin's own | Conflating channel-scoped moderation with cross-conversation administration is what the identity split exists to prevent, and an admin's chat identity is membership-gated like anyone's | FR5. [SPEC-MODERATION.md](./SPEC-MODERATION.md) for channel-scoped moderation |
| Granting or revoking admin status from a vended session | Minting the authority a session runs under, from inside that session, is a privilege-escalation path | [SPEC-ADMIN-IDENTITY.md](./SPEC-ADMIN-IDENTITY.md) - who an admin is and how the authority is vended |
| Acting as a user | Every action is attributable to the identity that took it, and impersonation breaks that by construction. No identity this exchange vends can act as a user other than the caller | FR2. A person's grant and an assistant's grant never name each other's kind of resource |
| A standing server-side bearer for attachments | A standing bearer is a credential nobody asked for that exists between requests. The client presigns with the vended credential instead | FR8. The credential is hard-bound to one channel's key prefix for its TTL |
| A session that outlives a turn | Role chaining caps an assumed session at one hour, so a turn that outlives it reaches its own expiry rather than silently re-resolving an identity after the model has run | FR11. The expiry is the safe failure |
| Blanket message deletion of a departed person's history | An offboard that blanks authorship makes the record unreadable, which is a different harm from the one it avoids | FR14. The shipped path is hard delete with a placeholder author; `offboardMode` is declared for a per-conversation-type choice of a named deactivated author instead, and no handler reads it |

## User Experience Description and Mocks

This document has no end-user surface. What a developer and an operator actually do with it is four things.

**A developer integrates an identity provider by pointing it at one endpoint.** The frontend presents an identity token to `POST /exchange-credentials` and receives short-lived AWS credentials plus the caller's own `userArn`. Nothing else is required of the client: it does not choose a role, does not declare a classification, and cannot widen what it was given. Requesting a narrower session is the only lever, and it is a list of capability names plus an optional `channelArn`. The deployer-facing walkthrough is [IDENTITY-PROVIDER-GUIDE.md](../../../guides/user/IDENTITY-PROVIDER-GUIDE.md).

**An operator crosses the plane boundary deliberately, once per action.** Listing conversations across classifications happens on their console session from the admin credential exchange. Redacting, deleting, changing membership, opening an attachment or reading stored message content each require a fresh request on that capability's own route (`POST /exchange-credentials/admin/<capability>`) naming one `channelArn` and a stated reason, which vends a different identity for a shorter time and records that it did. A denial therefore fails that one action rather than the read it was launched from, and an operator who took no privileged action holds no privileged credential.

**An operator verifies the pin rather than trusting it.** Running `backend/scripts/deny-test-credential-exchange.mjs` provisions a real channel and lets IAM answer: the same send succeeds bearing the caller's own ARN and is refused bearing another person's. Running `backend/scripts/deny-test-session-classification.mjs` reads the trust condition off the deployed roles before testing a matching, a mismatched and an absent assertion. Neither is a code review, which is the point.

**An operator offboards a person.** Hard delete removes the `AppInstanceUser`, its admin-plane twin, the memberships and the person's own records, by AppInstanceUser id for every issuer, and keeps their battle votes and feedback (§6a), so historical messages render a "Former member" placeholder author, and it is the only mode a handler performs. A person deleted at their identity provider is offboarded by that event; a person disabled there is refused at their next vend, and re-enabling them admits the next one. Deactivate - keep the identity, rename it to a placeholder, flag it, remove memberships and delete the auth user, so "who said what" survives - is the alternative `offboardMode` is declared to select per conversation type, and no handler reads that field (FR14). An immediate downgrade is a separate act from either: remove the memberships, because in-flight credentials carry the old role until they expire, and a disable at the issuer takes effect at the next vend.

**OPEN:** FR14's unknown-sender fallback is a requirement either mode depends on - no surface may render a blank author - and this document does not name the resolver that implements it or a test that pins it.

The rest of this document is the mechanism: the model, the vend roles, the planes, the lifecycle, and the invariants the requirements above are satisfied by. Section numbers are retained because other documents cite them.

## 1. Why

For an interaction layer to be safe and open at the same time, every actor - a classified user, an external person routed in from a connector, a guest, the assistant itself - must participate **at exactly the capability they should, and only as themselves.** Because AgentEchelon is built on AWS-native services (Amazon Chime SDK + Cognito + STS), it can make that an **IAM decision, not application logic**: a backend exchange vends short-lived AWS credentials **scoped by IAM** to the caller's own identity at a classification the caller is cleared for. Identity becomes infrastructure-enforced, evaluated before any request is processed.

## 2. Who benefits

- **The business** plugs in any identity provider (its SSO, a service login, or the built-in Cognito) and gets a uniform, capped, audited access model without writing access logic per integration.
- **Every participant** is provably acting *as themselves* - they cannot impersonate another identity or exceed their classification, regardless of a client bug or a routing mistake.
- **Operators** get one credential chokepoint to reason about (and to revoke at), instead of access scattered across the frontend and the identity provider.

## 3. Experiences enabled

- **Classified users** sign in and act within the set their classification grants, bearer-bound to their own identity.
- **Federated externals** (a routed support agent, an on-call engineer) join from the business's identity provider, bound to the conversation's classification, scoped to the one conversation they are invited to ([SPEC-FEDERATED-PARTICIPANTS.md](./SPEC-FEDERATED-PARTICIPANTS.md)).
- **Guests** get a deliberately minimal, single-conversation access level.
- **The assistant** acts as its own identity (never as a user) - see the composition section.

## 4. The exchange

The frontend presents an identity token to `POST /exchange-credentials`; a connector never does, because it names a person and never authenticates one ([SPEC-CONNECTORS.md](../../communication/SPEC-CONNECTORS.md)). The Lambda:
1. **validates the token** against a declared issuer (the edge authorizer on `PersonApi`, never answered from its cache on this route, verifies the token against the registry entry its `iss` names, a one-conversation issuer's included, because the exchange is one of the two routes such a person calls; the handler reads that entry, the subject and the verified claims from the authorizer's context, `tokenCallerOf` in `backend/lambda/src/lib/vend.ts`),
2. resolves the caller's AppInstanceUser and classification from the **validated claims** (never the request body - IDOR guard),
3. creates the caller's `AppInstanceUser` when it does not exist yet, as the only minter (§4b),
4. `sts:AssumeRole`s the matching capped role **with a `person` session tag carrying the AppInstanceUser id**, and
5. returns short-lived credentials + the caller's own `userArn`, which is the client's identity from then on.

Steps 2 and 3 run through one minter, `mintOrResolvePerson` (`backend/lambda/src/lib/person-identity.ts`): the caller's (registry issuer id, declared subject) resolves to a UUID v7 AppInstanceUser id through `Identities`, minted and reserved on the first exchange, or bound once to a pre-assigned `pending` row for a `provisioned-only` issuer.

The assumed role then **pins the bearer** to the caller's own identity in IAM:

```ts
// the role's channel-action grant, bearer scoped to the session's own AppInstanceUser:
resources: [ `${appInstanceArn}/user/${'${aws:PrincipalTag/person}'}` ]   // not …/user/*
```

So the credentials are bounded two ways at once: the **classification** (which role) and the **bearer** (which AppInstanceUser ARN). Each classification role's trust policy names one principal, the exchange Lambda's execution role (`CredentialExchangeRole`), and carries the same condition on both `sts:AssumeRole` and `sts:TagSession`: `aws:RequestTag/person` present (`StringLike` `*`) and `aws:RequestTag/classification` equal to the role's own classification (`StringEquals`) (`makeExchangeRole`, `identity-stack.ts`, through `PrincipalWithConditions`). An un-tagged assumption, or one asserting another role, is refused at `AssumeRole`. The admin-plane role (`ExchangeRoleAdminPlane`, in `admin-services-stack.ts`) takes the same shape with `classification` equal to `admin`, and its one trusted principal is the admin credential exchange's execution role (`AdminCredentialExchangeRole`). What IAM does not condition is the VALUE of `person`: any value satisfies the trust policy, so that the tag names the caller rests on the exchange deriving it from validated token claims (step 2). The synthesized trust documents are asserted by `an-exchange-role-cannot-be-assumed-un-pinned` (conditions present on both statements and identical; the per-classification value is read from `makeExchangeRole`, not asserted); the live `deny-test-session-classification.mjs` reads only the deployed `sts:TagSession` statement, so that the deployed `sts:AssumeRole` statement carries the condition is synthesized-policy evidence, not live evidence (**OPEN**).

### 4a. Assistant pin

An assistant is pinned the same way a person is, because an `AppInstanceBot` and an `AppInstanceUser` are principals of the same kind on the same control plane. A person's classification role names the caller's own user ARN through a session tag; an assistant's acting role names its own bot ARN the same way:

```ts
// the assistant acting role's channel-action grant, bearer scoped to the session's own bot:
resources: [ `${appInstanceArn}/bot/${aws:PrincipalTag/bot}` ]   // not …/bot/*
```

**One role per classification, any number of assistants.** The turn-running Lambdas are built per classification and shared by every assistant in it, so a grant on them cannot name one assistant, and a role per assistant would put every new assistant behind a deploy and an IAM write. So each classification has one acting role (`assistantActingRole`, `agent-classification-common.ts`), and what selects the assistant is the session: the vend assumes the role per turn with the session tags `assistant`, `classification`, `role` and `bot`, and `SourceIdentity` set to the assistant, so CloudTrail names the assistant on every call the turn makes (`assistant-vend.ts`). Nothing about a particular assistant is written into IAM, which is why adding one is data, not a deploy. This is the person case exactly: one role serves a role and `${aws:PrincipalTag/person}` selects the caller within it; one role serves a classification and `${aws:PrincipalTag/bot}` selects the assistant within it.

**One mechanism, stated once: the routing record, the vend, the acting role.** The router decides which assistant answers a message, and before it dispatches a turn it writes that decision to the classification's routing table, keyed by the turn's correlation id, naming the bot and the classification, with a seven-day TTL (`recordTurnRouting`, `lib/turn-routing.ts`; `invokeAsync` in `router-agent-handler.ts`). A second write for the same correlation id must name the same bot, so a turn in flight cannot be re-pointed. The channel flow records its own routing decisions, and the battle orchestrator records a duel's rebuttal round under its own correlation id; nothing else holds `PutItem` on the table. The processor never names an assistant: it invokes the vend synchronously with the correlation id (`vendAssistantSession`, `lib/assistant-session.ts`). The vend reads the record strongly consistent, refuses one that is missing, expired or for another classification, resolves the assistant and its assistant role from the assignment records rather than from the caller or the record, validates the assistant id, and assumes the acting role (`assistant-vend.ts`). Credentials ride only the synchronous response, never an asynchronous event, because the Lambda service keeps and replays asynchronous events.

**The acting role's trust policy names the vend and nothing else, which is what makes the pin IAM-enforced.** It requires `aws:RequestTag/classification` equal to the role's own classification, `aws:RequestTag/role` among the assistant roles the deployment declares for the classification (`deployedRoles` in `assistant-profile-stack.ts`; a role the shipped catalog offers is declared by naming its assistant in `profiles`, so one the deployment does not name is refused), and `aws:RequestTag/assistant` and `aws:RequestTag/bot` present, and the conditions sit on `sts:AssumeRole` as well as on `sts:TagSession` (`PrincipalWithConditions`, `assistantActingRole`) - conditioning only the tag call looks equivalent and is not, because the vend could then assume the role without tags and skip the pin. The processor, the router, the flow and the task service cannot assume the acting role at all. IAM requires the `assistant` and `bot` tags to be present, not to hold particular values; which bot a session names is bounded by the vend reading the routing record and the assignment records, and by the bearer condition on the bot's own `classification` tag (below). The trust policy also permits the vend `sts:SetSourceIdentity` with no condition, so that the source identity names the assistant is the vend's code (`assistant-vend.ts`), not an IAM condition. The classification roles take the same shape (§4): `person` present and `classification` equal to the role's own classification, on `sts:AssumeRole` and on `sts:TagSession`, so a vend cannot mint a role it was not asked for and an un-tagged assumption is refused.

**The acting role grants, the boundary caps, and both are needed.** The role's policies grant what a turn uses: the turn's channel actions in channels tagged with its own classification, bearing `.../bot/${aws:PrincipalTag/bot}` only when that bot is tagged with the same classification; each assistant role's company context, conditioned on `aws:PrincipalTag/role` (`roleContextStatements`); the CloudWatch and Logs reads, conditioned on the `ops` role; and every other grant the turn needs, moved from the processor's own role (`assistant-profile-stack.ts`). The boundary is an allow-list of the services a turn uses (`BoundaryTheServicesATurnUses`), in which S3 is allowed only on the unclassified key families a turn uses and on the `context/` and `platform-knowledge/` prefixes the classification grants, objects and listing alike (`BoundaryObjectsATurnUses`, `BoundaryListingItsOwnPrefixes`), so a mistaken S3 grant on the acting role still cannot read another classification's documents and no other classification is named; plus Denies: no `iam:*`, `sts:AssumeRole`, `sts:TagSession` or bot tagging (`AnAssistantNeverEditsIdentityOrChains`), so a session can neither edit its own policy, chain into another role nor rewrite an identity's tags; no channel and no bot outside this classification, so an untagged channel or bot is refused rather than let through; and no telemetry read unless the session's assistant role is an observability role.

**Bots carry their own identity tags.** The provisioner stamps every bot with `classification`, `assistant`, `role` and `provisioner` in the create request (`provisionerTags`, `lambda/src/lib/assistant-provisioner.ts`; a duel alt's assistant is `alt-{role}-{classification}`), and may write only those keys (`RUNTIME_ASSISTANT_TAG_KEYS`, `runtimeAssistantProvisioningAllow`). The acting role's bearer condition reads the bot's `classification` tag, which is the second layer behind the `bot` session tag. No turn-path principal holds an `iam:` action (deploy-time custom resources hold `iam:PassRole` and `iam:CreateServiceLinkedRole`): `admin-experiments.ts` assigns an alt by writing the assignment record, and the vend picks the new assistant up once its assignment index cache expires, up to 60 seconds. A session already minted lives up to one hour, so a change of assignment reaches every turn only after both.

**The assistant NAME stays the platform handle, and it is an identifier rather than a display label.** The ARN identifies the principal inside one deployment, the way a `sub` does for a person; the name identifies the assistant across analytics, SSM and a portable profile, where an instance-bound ARN may not appear ([SPEC-PORTABLE-PROFILES](../assistants/SPEC-PORTABLE-PROFILES.md)). Renaming an assistant is therefore creating a different one, not editing one.

**Both halves of the lifecycle.** Every assistant identity is the provisioner's ([ADR-048](../../design/decisions/048-an-assistant-is-not-a-classification.md), amended 2026-10-24), so the provisioner deletes what it built, on the one role that holds the grant: a console retire deletes the identity and its Amazon Lex bot, a stack's seed asks the provisioner to delete the assistants it declared when their duel or classification is withdrawn (a role is withdrawn only once every assistant in it is retired), and a teardown deletes what the directory still records, the same way deleting a person deletes their `AppInstanceUser` (`user-management.ts`). Every action on an identity is strict on the resource tags `classification` and `provisioner`: strict rather than `IfExists`, so an absent key denies at IAM instead of silently allowing. An identity nothing provisioned is therefore unreachable by every provisioner; that is why a `/bot/*` grant elsewhere reads wider than it reaches.

**What makes this safe against the prompt-injection case is ORDERING, and it is the property to preserve.** The assistant identity is fixed by the routing record before the turn is dispatched, and the processor adopts the session **before the model runs** (`adoptTurnIdentity`, `assistant-async-processor.ts`). No model output exists at the moment the identity is fixed, so nothing the assistant is told can change whose credentials it then holds. An implementation that resolved the identity from anything the model produced, or that adopted the session later in the turn, would lose the property while still looking correct.

**The validated source is not always the channel tag, and the design is wrong if it pretends otherwise.** An ordinary turn resolves the assistant from the conversation's immutable `classification` tag and the profile registry. Two live paths do not: a battle or alt turn takes the identity from a caller-supplied request attribute checked against the alt roster (`router-agent-handler.ts`, `lib/battle-turn.ts`), and a handover takes it from a stored task field through the same gate. Both are validated before the routing record is written, so the ordering property holds; neither is derived from the channel tag. What bounds these paths is that the record can only name a bot the vend finds in this classification's assignment records, and the trust and bearer conditions above.

**THE SESSION MUST BE HELD BY THE PRINCIPAL THAT SENDS, WHICH IS NOT ALWAYS THE ONE THAT RESOLVES.** Credentials do not cross a Lambda invoke, and a field in an invoke payload is whatever the invoker put there, so the routing record is the carrier: the router resolves, writes the record, and dispatches; the processor asks the vend with the correlation id and gets the session the record allows. The processor's own role holds its bootstrap - logs, invoking the vend, and the admin error alert posted as the admin assistant, whose bearer is pinned to admin-plane bots by tag - and the processor's own records about a turn (abuse counters and the cost circuit, turn state, the message-analytics row, the triage dispatch), which it writes on ambient clients and the acting role does not hold. Every other AWS client it reaches is wrapped by `sessionClient` and a call made without a session is refused by IAM (`assistant-profile-stack.ts`, `assistant-async-processor.ts`). An event naming a bot the turn was not routed to is refused. The router itself, once it has validated which bot answers, records an invocation-scoped decision and adopts a messaging-scoped session (`speakAsRoutedAssistant`), so every Amazon Chime SDK messaging call it makes after that, reads included, goes out on that assistant's session. Its DynamoDB and SSM reads, the drift scope search (`live-drift-flow.ts`, on a plain client) and channel creation stay on its own role, which holds no send or update as a bot; the drift link message goes out on the session. The channel flow speaks through per-assistant clients on vended sessions and holds no `SendChannelMessage` or `UpdateChannelMessage` (`channel-flow-processor.ts`, `channel-flow-stack.ts`); the battle orchestrator holds no Amazon Chime SDK grant and posts its placeholder and notices on per-side sessions (`battle-orchestrator.ts`, `battle-stack.ts`).

**A turn that cannot be vended a session does not act.** The vend refuses rather than returning a wider identity, and `adoptTurnIdentity` throws, failing the turn; the asynchronous invoke's retries and failure destination handle a transient fault. There is no fallback identity, because the processor's own role holds nothing a turn could act with.

**The session is released between turns.** A warm container handles turns for the same classification but not necessarily the same assistant, and a duel turn inheriting the other side's session would answer as the wrong side, so the processor releases the session at the end of every turn, beside the turn's assistant and assistant role (`endAssistantTurn` in `lib/async-processor-core.ts`, over `releaseAssistantSession` in `lib/assistant-session.ts`).

**Work a turn stopped waiting for finishes on its session.** A voiced send, a welcome prompt and a context read race their call against a deadline and go on without it, and the call keeps running: a model reply arrives later and its output guardrail is sent after it. Such a call is held (`holdSessionFor` in `lib/assistant-session.ts`), and every invocation that adopts a session ends through `releaseAfterHeldWork`, which waits for held work to settle before it releases the session: the processor through `endAssistantTurn`, and the router's handler on every exit. So the late call's guardrail and any fallback model call go out as the assistant that started them, never on the function's own role (the processor's holds no `bedrock:ApplyGuardrail`) and never on the next invocation's session in a warm container. A read the router needs only for some runs is started on first use and awaited by its user, so it is never left in flight: an event run reads the room's roster only when a mention needs it (`eventRunDeps` in `router-agent-handler.ts`). Verified by: `a-turn-acts-as-the-assistant-it-was-routed-to.test.ts` ("work a turn stopped waiting for still runs on its session") and `a-router-read-ends-with-its-invocation.test.ts`.

The assistant session inherits the rest of the exchange's shape: it carries no `sts:AssumeRole` of its own, so a turn cannot re-assume; the acting role's trust policy names only the vend; and assumption itself requires the tags, so the role is never assumed un-pinned. Role chaining caps an assumed session at one hour, so a turn that outlives it (a long task, a queue drain, an amendment fold) reaches its own expiry rather than silently re-resolving an identity after the model has run.

**Each assistant is narrowed inside its classification.** The vend passes session policies chosen from the assistant's approved definition out of the classification's catalog (`grantEdgesFor`, `assistantGrantCatalog`), so the effective permission is the acting role, its boundary and those policies together, and the definition store is part of the boundary. It is the person-side construction applied to an assistant, and like it, it can only narrow: two assistants holding the same assistant role may differ in whether they reach the classification's company context, platform knowledge and telemetry, and in which models they reach. Guardrails and context sources other than `company-docs` are not narrowed per assistant.

**Live deny-tests:** a session acts as its own bot and is denied any other, and is denied every other classification's conversations (`assistant-classification-boundary.spec.ts`); each acting role trusts only its own classification's vend, and no turn-running or routing role can assume it (`only-the-vend-mints-an-assistant-session.spec.ts`); no platform service can post as an assistant on its own role (`no-platform-role-speaks-as-an-assistant.spec.ts`).

### 4b. Issuers and the person id

A person is one `AppInstanceUser` ([IDENTITY-AND-ACCESS-MODEL.md](./IDENTITY-AND-ACCESS-MODEL.md) §1a). The exchange is where an issuer's record becomes that resource, and it is the only place one is created.

**The `Identities` index.** Its rows are `(registry issuer id, declared subject) -> AppInstanceUser ARN`, written by the exchange, at a sign-in or at binding (an invitation redeemed, or a registration claimed), and, for a `provisioned-only` issuer, ahead of the first sign-in by `provisionSubject` as a `pending` row that the exchange binds once. Keying on the registry id rather than the raw `iss` keeps a row stable when an issuer's URL or token version changes. The declared subject is `sub` by default, `tid` + `oid` for Microsoft Entra ID (its `sub` is pairwise per app registration), and org id + user id for Salesforce. The AppInstanceUser is authoritative, so a row whose AppInstanceUser is gone resolves to nothing.

**The issuer kinds.** The registry declares each issuer as one of:

| Kind | What it is | `provisioning` |
|---|---|---|
| `cognito-pool` | A Cognito user pool of the deployment's own: a customer pool with self sign-up, or a staff pool with no self sign-up | `on-first-sign-in` |
| `cognito-federated` | A SAML or OIDC provider federated into one of those pools, for example IAM Identity Center over SAML into the staff pool. It is the way in for SAML, and one of two choices for OIDC. The declared subject is the pool `sub`; the person is a pool account named by the pool username Cognito gives the provider sign-in (`<providerName>_<id>`) | `on-first-sign-in` |
| `oidc` | An OpenID Connect provider verified directly (Okta, Auth0, Ping, Keycloak): `issuer` (the exact `iss`), `discoveryUrl` and the keys it publishes, `audience`, `algorithm` and `tokenUse`. The declared subject is `sub` unless the entry declares `subject`. No Amazon Cognito resource is involved | as declared |
| `oidc-entra` | Microsoft Entra ID verified directly: one tenant, or a tenant template plus an allowlist of several tenants, and one token version | as declared |
| `host-assertion` | A host application that signs a short-lived assertion for its signed-in user, for example a Salesforce org; the registry pins its public keys, and `aud`, a short `exp` and a single-use `jti` are required (see "The host assertion" below) | `provisioned-only` |
| `guest` | The platform's own issuer for an anonymous visitor: short-lived tokens signed with a KMS key, a rotating server-stored refresh credential | `on-first-sign-in` |
| `invitation-link` | The platform's own issuer for a person who redeems a `link` invitation from its landing page with no sign-in. It signs no token: the redemption is the credential (§4c) | not declared: the invitation names the AppInstanceUser |

`on-first-sign-in` means the issuer is itself the gate, so a miss mints an AppInstanceUser. `provisioned-only` means a miss is refused and nothing is created: the subject resolves only to an AppInstanceUser pre-assigned to it. A third value, `scim`, for an issuer whose people a provider pushes, parses and is refused at synth as **NOT BUILT** (`NOT_BUILT_PROVISIONING`, `backend/lib/config/issuers.ts`).

**Pre-assignment (`provisionSubject`).** One operation writes a `provisioned-only` subject's `Identities` row ahead of its first sign-in: `status: pending`, naming a person who already exists or a fresh UUID v7 id (`backend/lambda/src/lib/person-identity.ts`). The row is only ever created: a subject that has a row or a revoked marker is left as it is. Two callers may ask for one, each through its own provisioner function in `Identity`, with the caller fixed in its environment, because a direct invoke attests nothing about who invoked it (`backend/lambda/src/provision-subject.ts`, `backend/lib/constructs/subject-provisioner.ts`):

- the admin backend, for `POST /users/provision` (`manage-users`), for every `provisioned-only` issuer, linking the subject to an existing person or to a new one;
- the connector webhook receiver, for a person a vendor event names under a subscribing connector's `provisioned-only` `personIssuer` (V8), always to a new person, which is reported `pending` and admitted nowhere until its first sign-in.

Two layers hold it. IAM: only the caller's own role may invoke its provisioner, and the provisioner's role may `PutItem` on `Identities` only under its issuers' keys (`dynamodb:LeadingKeys` `<issuer id>|*`) and only with a pending row's attributes (`dynamodb:Attributes`), with no `UpdateItem` or `DeleteItem`. The handler: the issuer must be one its caller provisions for and one the registry declares `provisioned-only`, and the connector caller never links an existing person. At the subject's first sign-in the exchange binds the row with one conditional update (`pending` to `active`, only for the issuer the row names, `bindProvisionedPerson`), creates the AppInstanceUser if it does not exist, and vends; two first sign-ins racing resolve to the one person. The edge admits a `pending` subject to the exchange alone, with no person in its context, and denies a `provisioned-only` subject with no row every route. Pre-assignment by an invitation, by the SCIM receiver and by an already-pinned session is **NOT BUILT**.

**The host assertion (A9).** A `host-assertion` entry pins its host's public keys by `kid` (`hostAssertion.publicKeys`: one or two, an RSA key of at least 2048 bits for `RS256` or a P-256 key for `ES256`) and an assertion lifetime (`maxMinutes`, default 5, at most 10). There is no discovery endpoint, so a rotation is the operator's: declare the next key beside the current one, then remove the old one. Its subject is `org` + `sub`; its clearance is a `mapping` (the permission-set claim) or a `fixed` set within its declared classifications, so an unmapped permission set reaches nothing; it is `provisioned-only` and never `admin: true`. The checks, in order:

1. The edge accepts an assertion on `POST /exchange-credentials` alone, the route never answered from the authorizer cache, and refuses it (401) on any other route before it records anything. The admin plane's edge does not declare the issuer at all.
2. It verifies the signature with the pinned key the header `kid` names, the header `alg` against the declared one (`none`, HMAC and an embedded key refused first), `iss` exactly, `aud` equal to the deployment id, `exp` present and no further ahead than `maxMinutes`, `iat` present with `exp - iat` within it, `nbf`, and a `jti` (`backend/lambda/src/lib/token-verification.ts`).
3. It records the `jti` in `Tokens` under `assertion-jti#<sha256(<issuer id>|<jti>)>` with a conditional put, so the same assertion presented again is refused (401). The edge's grant on `Tokens` is `PutItem` under `assertion-jti#*` alone.
4. The exchange consumes that record (`consumedAt`, conditional on it existing, unconsumed and unexpired) before it binds or vends anything (`backend/lambda/src/lib/host-assertion-exchange.ts`); its grant is `GetItem` and `UpdateItem` under `assertion-jti#*`, never `PutItem`, so an assertion that did not pass the edge has no record to consume.
5. It binds the provisioned subject (above) and vends at the classification the mapped permission set names, bearer-pinned like every other person. No handler but the exchange resolves a person from a host assertion (`callerPerson`, `backend/lambda/src/lib/auth.ts`).

Each refusal is counted by check: `AssertionRefused` in `AgentEchelon/HostAssertion`, dimensioned by `Check` and by `Issuer` and `Check`. Any signer in the host can sign for any of its users, so the host is trusted as one issuer, bounded by its classifications (R14). The widget checks that a posted assertion comes from a declared host origin and from `window.parent` before it presents it (SPEC-EMBEDDABLE-WIDGET, FR8). **NOT BUILT:** the Salesforce side: Apex signing with the org certificate and the post into the frame (O9). **NOT VERIFIED:** an assertion signed by a live Salesforce org; the deny-tests sign with a test-double key the registry pins.

**Verified by:** **NOT VERIFIED** on a deployment yet. The live checks are `backend/scripts/deny-test-host-assertion.mjs`, `backend/scripts/deny-test-pending-identities.mjs` and `backend/scripts/deny-test-admin-exchange.mjs`; each run is recorded here, dated, with its result. Offline: `the-edge-verifies-a-host-assertion`, `a-host-assertion-is-spent-before-the-exchange-vends`, `a-provisioned-subject-is-pending-until-its-first-sign-in` and `the-host-assertion-boundary` (unit).

**An account disabled at its issuer.** The `Identities` table keeps no copy of an identity provider's state: a row is `active` or `pending`, and whether the account behind it may still sign in is asked of its issuer at every vend, the first sign-in and each hourly refresh alike, before anything is minted, bound or recorded (`refuseInactiveAccount`, `backend/lambda/src/lib/vend.ts`, through `Directory.accountState`, `backend/lambda/src/lib/membership-source.ts`). The person exchange and the admin exchange's console session ask the same question through the same helper. Every other admin vend asks it too, because a console session outlives the moment it was issued: a per-capability credential and a team member's attachment read are minted only after the person the session names is read back to their subjects through the `Identities` `byPerson` index and one of their sign-ins at an issuer declaring `admin: true` is active there (`refuseInactivePerson`, `backend/lambda/src/lib/vend.ts`, through `accountStateOfPerson`, `backend/lambda/src/lib/membership-source.ts`). Admission asks it as well: a person a connector names (`resolveParticipant`, `backend/lambda/src/lib/connector-participants.ts`) or a host adds to its context conversation (`membershipHandler`, `backend/lambda/src/conversation-management.ts`) is admitted only when one of their sign-ins is active at its issuer, and a read that fails admits nobody; a host's remove asks nothing, so a disabled person can always be taken out. An account its issuer reports disabled or gone is refused `403 PERSON_NOT_ACTIVE` with nothing minted or recorded. A directory that cannot be read refuses `503 DIRECTORY_UNAVAILABLE` and vends nothing, because a failed read is never taken for an enabled account. A session vended before the disable lasts out its own lifetime, one hour at most, which is the accepted bound; re-enabling the account admits the next vend with no step on the platform's side.

**Reach comes from the issuer's declaration.** Each issuer declares a clearance source (a claim-to-classification mapping, a fixed classification set, the person's groups translated into AgentEchelon groups, or the one-conversation session at a named classification, `clearance: { oneChannel }`) and the classifications that source may grant. A claim value the mapping does not declare, and a provider group the entry does not translate, reach nothing, and an issuer entry that declares no source is refused at synth: there is no fallback reach. Adding an issuer widens authentication, and authorization only as far as its classifications and the values it maps: the bearer pin and the classification tag decide what any session reaches.

**A person's groups.** Each identity provider keeps its own groups, and the deployment keeps its own: the **AgentEchelon groups**, which are the keys of `groupClearance` and `membershipGroups` (`backend/lib/config/profiles.ts`), the console role groups `admins` and `team-members`, and the `team-<name>` groups. Every clearance, membership requirement, console role and team scope is decided on AgentEchelon groups and on nothing else. An issuer entry translates its provider's groups into AgentEchelon groups, so a provider group no entry maps reaches nothing, and a group an outside administrator names `admins` is not the AgentEchelon group `admins` unless the entry maps it there.

1. **The translation is per issuer.** A `cognito-pool` entry declares `groups: true`: its pool's groups are AgentEchelon groups, unchanged. Every other kind whose tokens carry groups (`cognito-federated`, `oidc`, `oidc-entra`) declares `groups: { "map": { "<provider group>": "<AgentEchelon group>" } }`, read from the entry's `groupsClaim` (default `groups`; `custom:groups` for `cognito-federated`), where a provider group is the value exactly as the token carries it (an Entra group ObjectId, never a display name). Synth refuses a target that is not an AgentEchelon group. Nothing a provider names becomes a pool group, and an `oidc-entra` allowlist of several tenants maps each tenant's ObjectIds in its own entry.
2. **Every decision reads the translated groups, within the entry's classifications.** `groupClearance` turns them into classifications, each within the issuer's `classifications` (`heldWithinIssuer`). The console role and team scope read the same translated groups: `admins` and `team-members` count only for an entry declaring `admin: true`, and a team scope reaches only assistants of classifications inside the entry's classifications. `groupsOf` (`backend/lib/config/issuers.ts`) is the one place the translation happens, and `consoleRoleFor` (`backend/lambda/src/lib/vend.ts`), the team scope (`backend/lambda/src/admin-credential-exchange.ts`, within the entry's classifications) and `isAdmin` (`backend/lambda/src/lib/auth.ts`) read only what it returns, so a raw provider group reaches none of them. A translating entry marks its administrators by mapping a provider group to `admins`; `adminGroups` names which of a pool's own groups mark an administrator, and synth refuses it on a translation.
3. **One way to translate groups** (tenet D9). A `mapping` (a claim straight to classifications) stays for claims that are not groups, such as Entra app roles and a host's permission set, and synth refuses a `mapping` whose claim is the entry's groups claim.
4. **A groups claim is read as whole values.** An array is its values; a string is one value and is never split; a value is compared exactly. An Entra overage marker (`_claim_names.groups`, `hasgroups`) and a claim the provider marks as truncated reach nothing. `providerGroupsOf` reads them; `claimValues`, which splits a string on whitespace and commas, is used for a pool's own groups alone, whose names carry neither.

| `oidc` | The ID token's declared groups `claim` | Undetermined; the exchange's recorded `clearanceDecision` is evidence of the last sign-in, never a grant |
| `oidc-entra` | The ID token's `groups` claim (group ObjectIds) | As for `oidc` |
| `cognito-federated` | The provider's groups, written by the provider's attribute mapping into the pool attribute `custom:groups` and carried on the pool's ID token | As for `oidc` (`translatedGroupsClearanceSource`): the pool attribute is a copy of the last federated sign-in, so it is not read as a grant. A pool group on a federated person's account is not one they hold, so the admin roster and `personsInGroup` leave the entry out |

**A provider is verified directly or federated into the pool, and the deployment chooses.** A production `oidc` entry is accepted, and so is a single-tenant `oidc-entra` entry on a deployment with a pool; a deployment needs an Amazon Cognito user pool only when an entry declares one. The rejected alternative routed every generic OIDC provider and every single-tenant Entra tenant through `cognito-federated`, so the pool was the one verifier and the `claims` contact copy was needed only for the remaining direct cases; it made the pool a dependency of any deployment whose people sign in with OIDC. Choosing the direct path accepts what federation avoids: the person's contact claims are copied under `claims` (encrypted, replaced at each sign-in, erased with the person), there is no live directory, and there are no lifecycle events. A provider is declared on one path only: one human signing in through both is two people, and moving a provider between paths re-keys its people, which is done by the second-issuer link or a fresh deployment, never by declaring both. A direct entry:

- **Presents the ID token.** A browser sign-in redeems the code at the provider and presents the ID token (`tokenUse: "id"`), whose `audience` is the client id the sign-in screen uses. The provider puts the groups claim in the ID token for the `openid email profile` scopes the client asks for (Okta: a groups claim filter on the authorization server; Auth0: an Action; Entra: `groupMembershipClaims` on the app registration).
- **Names what makes its `iss` its own.** An issuer whose `iss` is shared across organizations declares `requiredClaims`, and a token without them is refused at the edge; synth refuses a shared issuer it knows (`https://accounts.google.com`) without one (Google Workspace: `hd`).
- **Bounds its token.** `maxLifetimeMinutes` (default 90, `DIRECT_TOKEN_MAX_MINUTES`, the longest Entra randomizes an access token to) caps `exp - iat`, as `maxLifetimeSeconds` does for the guest and host kinds.
- **Is offboarded by the console.** A direct person has no lifecycle events: removal at the provider stops new tokens, and the console's offboarding removes the `Identities` row, the AppInstanceUser and their memberships ([ADR-058](../../../design/decisions/058-offboarding-runs-by-app-instance-user-for-every-issuer.md)). A person the provider disables is refused once it stops issuing them tokens ("An account disabled at its issuer", above). **NOT BUILT:** acting on a person whose recorded `clearanceDecision` is older than `recordMaxAgeDays` beyond flagging it; SCIM is the event path, and `provisioning: scim` is refused at synth. A direct provider's administrators are not listed for the admin notification channel, whose members are read by listing a group (`Directory.admins`): **NOT BUILT**.

**The pool path keeps a provider's groups on the pool account,** and Cognito requires the app client to be able to write a mapped attribute, so the path carries controls the direct path does not need:

- **Writing `custom:groups` is the provider's alone.** Cognito writes a mapped attribute only when the app client lists it in `WriteAttributes`, and a client that lists it lets any holder of its access token rewrite it with `UpdateUserAttributes`. A `cognito-federated` entry with `groups` signs in through its own app client: the authorization code flow and refresh only, no `USER_PASSWORD_AUTH`, SRP or custom auth flow, `custom:groups` writable, and allowed OAuth scopes that exclude `aws.cognito.signin.user.admin`, the scope `UpdateUserAttributes` requires. Its providers are listed in that client's `SupportedIdentityProviders` alone, and `WebClient` and `AdminWebClient` list `COGNITO` alone. Its id is published as the stack output `UserPoolFederatedClientId` and read by both apps as `VITE_FEDERATED_CLIENT_ID`, which also refresh a federated session on it. Synth refuses `tokenUse: "access"` on a translating `cognito-federated` entry, since Cognito carries custom attributes on the ID token alone. `custom:groups` is read only from an ID token whose `identities` claim names the entry's provider, which Cognito issues only through the federated client, so a local account's value is never read; no code writes it.
- **A stale value fails closed.** Cognito keeps a mapped value when the provider stops sending the attribute, and SAML providers and Entra usually omit an attribute that has no values, so a person removed from their last group would keep it. Synth refuses `groups` on a `cognito-federated` entry unless it declares `emptyGroupsSent: true`, the operator's statement that the provider sends the attribute empty. **OPEN:** which supported providers can.
- **The value has a shape and a size.** Cognito flattens several values into one string in square brackets, comma-separated, with non-alphanumeric characters URL form-encoded. The reader decodes each value before it splits, so a group keeps its spaces, and a value it cannot parse reaches nothing. A mapped value longer than 2,048 characters fails the sign-in at Cognito, so a provider whose people hold many groups is configured with a groups filter or verified directly.

**On a deployment with no pool,** the AgentEchelon groups are the ones the deployment declares in `profiles`, and a team is named by the `ownerTeam` an assistant's profile declares or the console's ownership assignment, so a provider group mapped to `team-<name>` reaches that team's assistants with or without a pool.

**A pool's people are every entry on the pool.** The pool's own entry and each `cognito-federated` entry on it key their `Identities` rows under their own registry ids, and the people of each are pool accounts, so offboarding (its delete step and `sweepPool`, `backend/lambda/src/lib/offboarding.ts`), the offboarding console, person export and user management ask for every id on the pool (`issuerIdsForPool`). Every Admin call addresses a pool account by its pool username: Cognito accepts a `sub` as `Username` for a local user only ([AdminListGroupsForUser](https://docs.aws.amazon.com/cognito-user-identity-pools/latest/APIReference/API_AdminListGroupsForUser.html): "must be the sub of a local user or the username of a user from a third-party IdP"), so a `sub` the pool does not know by that name is resolved through `ListUsers` on the `sub` attribute (`bySubjectOrUsername`, `backend/lambda/src/lib/cognito-pool-directory.ts`). Every role that reads one pool account by subject is granted `ListUsers` beside it. That lets those roles list the pool's accounts as well as read one, which is the accepted cost; the rejected alternative recorded the pool username on the `Identities` row and carried it through every directory reader. A pool lookup that fails is an error, never "no account". **Verified by:** `backend/test/lib/a-federated-pool-account-is-addressed-by-its-username.test.ts`, and `backend/test/a-pool-read-by-subject-can-find-a-federated-account.test.ts` for the grant.

**SAML without a pool is NOT BUILT.** SAML reaches this deployment only by federation into a pool. A direct `saml` kind would be one adapter and one registry entry, under the rules in [IDENTITY-PROVIDER-GUIDE](../../../guides/user/IDENTITY-PROVIDER-GUIDE.md#other-issuers).

**Contact lookup reads the issuer's directory.** Each registry entry also declares a `directory` adapter that reads the issuer's own store live: `cognito` (`AdminGetUser`), `identity-store` (IAM Identity Center `DescribeUser`), `graph` (Microsoft Entra ID through a connector), `connector:<id>` (for example a Salesforce User), `scim`, or `claims`. Every lookup starts from the AppInstanceUser ARN. A name or contact address is fetched per use and never copied, except under `claims`, which is only for an issuer with no directory: the exchange keeps the contact claims (`email`, `name`) of the person's last sign-in under `<personId>#contact#<issuerId>` in the user-profile table, encrypted with a customer managed key, replaced at each sign-in, expired 90 days after the last one and erased with the person (`backend/lambda/src/lib/claims-directory.ts`). A failed write is logged and never refuses the credential. A `cognito` directory answers no contact for an account the pool reports disabled. **As built:** `cognito`, `claims` and `none`; `identity-store`, `graph`, `scim` and `connector:<id>` are refused at synth as **NOT BUILT**.

**One human through two issuers (B7).** Both `Identities` rows point at one AppInstanceUser. A second issuer is added only by a session already pinned to that AppInstanceUser plus the second issuer's token, in one call, so an address match never binds one. As built: the pinned session is the caller's own token on `Authorization`, resolved by the edge to an active row; the second token is `linkIssuer.token` in the body, verified by the exchange with the edge's checks (`LINK_ISSUERS`, every issuer but a guest and a host); the second subject's row is one conditional put, and the link is written to the access log as `identity_linked` (`backend/lambda/src/lib/issuer-link.ts`). A subject that already has a row is never moved, a person holds one subject per issuer, and a guest, a host assertion, a one-conversation issuer and a `provisioned-only` issuer are never linked this way.

**A visitor becomes a person (B6).** Path A, the bind (P-11): a first sign-in that presents the visit's sign-in hand-off (`bindGuest`: the single-use nonce the widget's guest refresh minted and the secret only the tab the widget opened receives, so a forwarded link binds nothing) is bound to the visitor's AppInstanceUser instead of minted. The exchange removes the AppInstanceUser's expiration, then in one transaction consumes the refresh credential the hand-off names, revokes its family, writes the account's row, deletes the guest issuer's row and spends the hand-off; a subject that already has a row is refused (`backend/lambda/src/lib/guest-bind.ts`). The account is vended at its own classification, never the guest's, and the exchange opens the visit's continuation at that classification, tagged with the visitor's conversation and AppInstanceUser and seeded as a claim's is, named in the answer (`bound.conversationArn`). Path B, the claim (P-12): a registration is claimed with a single-use `claim` token by a signed-in account, which opens a `customer-engagement` conversation tagged with the visitor's conversation (`backend/lambda/src/guest-upgrade.ts`). Both are described with their refusals in [GUEST-ISSUER](../../../guides/admin/GUEST-ISSUER.md#becoming-a-person).

**An AppInstanceUser before its sign-in.** Pending and guest AppInstanceUsers are created by the exchange with an expiration. A guest's AppInstanceUser has an `Identities` row under the `guest` issuer from its first message. A pending invitee, one the deployment does not yet know, has no `Identities` row until redemption binds one; a single-use token names its AppInstanceUser until then (§4c). The expiration counts from creation, so it would delete the person unless binding removes it. Whether binding can remove an existing expiration is **OPEN (O13)**: AWS documents `ExpirationSettings` on `PutAppInstanceUserExpirationSettings` as optional and does not state that omitting it clears one. The bind calls it with no settings, and the live probes are row A4 of `backend/scripts/deny-test-upgrade.mjs` and row S3 of `backend/scripts/deny-test-invitations.mjs`, owed with the first deploy. If it cannot, pending invitees and visitors are created without an expiration, and a low-frequency sweep deletes the AppInstanceUsers whose invitation expired unredeemed; the sweep is time-based because the absence of a redemption is not an event that can be sourced (tenet D6). That fallback is **NOT BUILT**.

**The session tag.** The bearer pin names the AppInstanceUser through the `person` session tag, which the exchange sets to the AppInstanceUser id (`backend/test/the-bearer-pin-is-the-person-tag.test.ts`).

**As built.** The registry (`backend/lib/config/issuers.ts`), the `Identities` index keyed `<registry id>|<declared subject>` and the one exchange that serves every entry exist. A `oneChannel` issuer's people are vended the one-conversation session on the `restricted` role (`oneChannelVend`, `backend/lambda/src/credential-exchange.ts`), and a console session only an issuer declaring `admin: true` can get. A `guest` issuer's visitors are minted by guest start, an entry point of the same exchange, and vended their own conversation on the guest-session role (`backend/lambda/src/guest-session.ts`, [GUEST-ISSUER](../../../guides/admin/GUEST-ISSUER.md)). A `host-assertion` issuer's assertion is verified at the edge against its pinned keys, spent once and bound to a pre-assigned person (above). A visitor binds by path A and claims by path B (above), and a pinned session links a second issuer. An invitation's invitee is minted by this exchange and redeemed through it (§4c). **NOT BUILT:** the `directory` adapters past `cognito`, `claims` and `none`.

### 4c. Invitations

A member invites somebody who has no account yet into a conversation (M-10, M-5; `backend/lambda/src/invitations.ts`, in `Conversations`). The invitation is a `Tokens` record of kind `invitation`, keyed by its token's hash, naming the conversation, the issuing AppInstanceUser and the invitee's AppInstanceUser, never an address: the address the inviter gives is where the one transactional email goes, and it is stored nowhere. The email is sent by `Notifications`, which holds the deployment's only SES send grant: the invitations function hands it to the `TransactionalMail` function by its fixed name (`backend/lambda/src/lib/transactional-mail.ts`). A deployment that does not declare `notifications` emails nothing, and the inviter is handed the link. The invitee is minted by this exchange on the invitations function's invocation (`mint-invitee`, `mintInvitee` in `backend/lambda/src/lib/person-identity.ts`): a fresh AppInstanceUser created with its expiration, at the invitation's own expiry, and no `Identities` row. It is added as a member of that one conversation, and membership before redemption reaches nothing, because no credential is vended as the invitee until its invitation is redeemed. The redemptions are this exchange's (`backend/lambda/src/lib/invitation-redemption.ts`), each in its declared mode only:

- **`sign-in`.** A first sign-in presents the token in the exchange's body (`{ invitation }`). The subject must have no `Identities` row; then the exchange removes the invitee's expiration and, in one transaction, writes the subject's row naming the invitee and consumes the record, so the person signs in as the invitee from then on. A subject that already has an account is refused (`wrong_account`) and nothing is bound, so a `sign-in` redemption never binds a second IdP record to an AppInstanceUser (R13); that account is added by sharing. A subject whose own clearance does not reach the conversation's classification is refused the same way.
- **`link`.** The landing page posts the token to `POST /invitations/redeem`, which takes no token and runs the kill switch, the per-address limit and the captcha first (L16). One conditional update consumes the record, and the exchange vends a session on the `link` role, pinned by its session tags to the invitee, the one conversation and its classification, for 15 minutes and not renewed. The role exists only with an `invitation-link` issuer in the registry, whose `fixed` set and the conversation type's `linkClassifications` both bound the classification, and its permissions boundary holds the read-and-post set on that one channel and nothing else (`backend/lib/constructs/invitation-link-issuer.ts`).

A redemption is refused, as a settled state, when the record is consumed (`redeemed`, or `redeemed_elsewhere` for a forwarded link), revoked, expired, of the other mode (`wrong_mode`), or issued by a person who no longer signs in as anybody. The landing page's read (`POST /invitations/peek`) answers what the token's holder may know and consumes nothing. Revoking an invitation (`POST /invitations/revoke`, or the console) marks the record and removes the invitee's membership, so a vended `link` session is refused on every channel call from then on. Offboarding deletes every invitation the person issued or is named by. The live deny-test is `backend/scripts/deny-test-invitations.mjs`. **NOT BUILT:** an invitation of a person who already has an account (they are added by sharing), a later sign-in that keeps a `link` invitee's conversation, resending an invitation, a request for a new invitation from a refusal, and invitations into meetings.

## 5. Vend roles

Every vend role is bearer-pinned; the action set and channel scope differ by role:

| Role | Who | Channel scope | Actions (all bearer-pinned, beyond session connect) |
|---|---|---|---|
| **restricted / guest** | federated externals, unauth widget visitor | **only channels they're a member of** (no discovery) | Send/Get/List messages, DescribeChannel, ListChannelModerators, ListChannelMemberships(ForUser), UpdateChannelReadMarker, UpdateChannel (owner rename) |
| **basic / standard / premium** | classified users | the classifications their own grants include (the IAM tag-gate) | the above + leave (`DeleteChannelMembership` own) + own-profile read/update |
| **admin (chat identity)** | admins | admin-plane channels only, **membership-gated** and **bearer-pinned to own** identity; held beside a member classification, that classification's role with the `adminPlane` session tag, which adds admin-plane channels and nothing else | the above |

**Never on any end-user role** (backend operations, not user credentials): `CreateChannel`, `CreateChannelMembership`, `CreateAppInstanceUser`, `UpdateChannelMessage`, `RedactChannelMessage`, `DeleteChannelMessage`, `DeleteChannel` - channel creation, member admission and administration flow through the create-conversation, share, and admin paths (their own roles). Moderation (`RedactChannelMessage`, `DeleteChannelMessage`) and cross-channel admin reads are never a chat role either; they are vended on the **admin plane** - a separate identity - described below. The exchange selects the role by the caller's **lifecycle state**, not just their group.

### 5a. Vend planes and per-request capability scoping

A request names the **capabilities** it needs and, optionally, a single `channelArn`; the exchange vends a session policy scoped to exactly those actions on that resource, intersected with the classification role's boundary. An STS session policy only ever narrows, so taking the capability set and channel scope from the request body is safe - a forged value can only reduce access. The default is the ordinary chat set (`view` + `participate`), so a client that sends no capabilities is unaffected. `view` + `participate` map to the read/send Amazon Chime SDK actions; `redact`, `delete`, `manage-membership`, `manage-channel`, and `rename` map to the mutating ones.

Every vend runs on one of two **identities**, never both in a request:

- **Chat plane (default)** - the caller's own `${personId}` on their clearance (or admin) role. Never an `AppInstanceAdmin`, so the Amazon Chime SDK membership-gates every read; long-lived (`EXCHANGE_SESSION_SECONDS`, default 3600s); may be scoped to `channel/*`.
- **Admin plane** (admins only, from the admin credential exchange in the `AdminServices` stack, `backend/lambda/src/admin-credential-exchange.ts`) - the caller's **separate** `${personId}-admin` identity, a standing `AppInstanceAdmin` that exchange provisions at the console session (idempotent). It is requested on the capability's own IAM-authorized route, `POST /exchange-credentials/admin/<capability>`, signed with a console session; the person exchange answers `identity: "admin"` and `identity: "console"` with `403 ADMIN_VEND_MOVED`. It is only ever vended a **channel-scoped, short-lived** (`EXCHANGE_MODERATION_SESSION_SECONDS`, default 1800s), **audited** credential, so cross-channel admin authority (an `AppInstanceAdmin` reads any channel without membership) never attaches to a broad chat credential. This is the two-identity split ([SPEC-ADMIN-IDENTITY.md](./SPEC-ADMIN-IDENTITY.md)).

Moderation capabilities (`redact`, `delete`, `manage-membership`, `manage-channel`) are refused on the chat plane; they are vended only by the admin credential exchange, on the capability's route, with a `channelArn`. On the admin plane that exchange serves three scoped sub-planes, each a different session policy and each exactly one request (never mixed):

- **Amazon Chime SDK moderation** - a `chime:*` session policy on the one named channel (redact / delete / membership / channel actions), bearer-pinned to `${personId}-admin`.
- **Archive read** - an `execute-api:Invoke` session policy on the admin conversations-messages API resource, so an operator reads a customer's stored message content short-lived and audited rather than from a standing role ([DESIGN-ADMIN-ACTION-IAM-ENFORCEMENT.md](./DESIGN-ADMIN-ACTION-IAM-ENFORCEMENT.md)). The conversation id is a path segment (`GET admin/conversations/{id}/messages`), so the session policy names that route completed with the one literal conversation id, and a credential for one conversation is refused at the gateway on another; the handler's classification check stands behind it.
- **Attachment read (S3)** - an `s3:GetObject` session policy on **only** the named channel's attachment keys. Two IAM-enforceable capabilities: `attachment-read` (assistant-generated deliverables under `generated-docs/<channelId>/*`, archive grade) and `attachment-read-uploads` (user-uploaded input under `attachments/<channelId>/*`, which may carry PII - moderation grade, flagged `sensitive` in the audit record). Because S3 ARNs condition on the object-key prefix, the credential is hard-bound to the one channel for its TTL. There is **no standing server-side S3 bearer**: the client presigns the `GetObject` with the vended credential. A future restricted admin role that omits a prefix from its boundary is denied that prefix at the IAM layer, so the split is IAM-enforceable, not a code-only gate. The attachments bucket ARN reaches the exchange via SSM (a CDK prop would be circular).

Every admin-plane vend emits a structured audit record (`_auditEvent: admin_scoped_credential_vend`) naming the admin identity, the channel, the capabilities, and the TTL.

## 6. User lifecycle

The **same `AppInstanceUser` persists**, under an opaque id that is not the `sub` (§4b); what changes is the role the exchange hands out and the memberships. Each transition has a definite owner:

| Transition | Owner / trigger | Effect |
|---|---|---|
| **Create** (native / federated) | the exchange, at first sign-in for an `on-first-sign-in` issuer, or when an invitation names an invitee not yet known | AppInstanceUser created by the one minter + `Identities` row + group set (a pending invitee has no `Identities` row until redemption binds one, §4c); a one-conversation issuer's person is admitted to the routed channel only, at the classification its issuer names. The sign-up trigger, user management and the scripts create no AppInstanceUser (`backend/test/single-entry-point.test.ts`) |
| **Promote** (guest → authenticated) | sign-in while holding a live guest session, or a registration claimed with a single-use token | either the guest AppInstanceUser, which already holds its `guest`-issuer `Identities` row, gains a row under the account's issuer and its expiration is removed (whether binding can remove it is **OPEN**, §4b), or a new conversation opens for the account's AppInstanceUser, tagged with the guest channel's ARN; the conversation type declares which (`upgrade`, both on `guest-visitor`), and neither merges by email (§4b) |
| **Classification change** (up or down) | admin sets the authoritative group | **new role on the next exchange** (it reads the live group); in-flight creds carry the old role until they expire (≤ session TTL). **Immediate downgrade** = remove memberships; a disable at the issuer is refused at the next vend, and does not end a session already vended |
| **Disable** | the issuer disables the account | the next vend (sign-in or hourly refresh) is refused `403 PERSON_NOT_ACTIVE` and nothing in `Identities` changes; a session already vended lasts out its lifetime (one hour at most); re-enabling admits the next vend (§4b, "An account disabled at its issuer") |
| **Offboard** | admin delete, or the issuer deleting the account | see the offboard modes below |

### 6a. Offboard mode
Two ways to offboard; the right one is **conversation/user-type dependent**:
- **Hard delete** - offboarding is not administration: it runs by AppInstanceUser id for every issuer. It removes the `AppInstanceUser` and its `-admin` twin (found by its owner tag), the memberships, the person's profile and task records, their turn state, their place in each conversation's context and battle setting, their own rows in the Aurora projection, the `attachments/<conversationId>/<personId>/` objects and their `Identities` rows, and the identity provider's user only when one exists. Nothing to delete is a 404, never a 200. Battle votes and thumbs feedback stay, still carrying the AppInstanceUser id, and so does the archive. The ARN stops resolving, so historical messages must render a **placeholder** ("Former member"), never blank. Fits external-customer/engagement cases where surfacing that someone left is undesirable.
- **How offboarding runs.** `offboardPerson` (`backend/lambda/src/lib/offboarding.ts`) removes, in this order: the `-admin` twin, found by its `owner` tag, with its memberships and its app-instance-admin; the person's memberships; their UserProfile row, their contact copies and their email preferences (`<personId>#notices`), their UserTasks partition (`principalId`) and the rows they own in an assistant's partition (`ownerPersonId-index`), the task records naming them as requester, owner or assignee (`AgentTasksTable`), their turn-state stop records, their entries in each conversation's member identity lookup and an onboarding intake that is theirs (`ChannelContextTable`), their name on a battle setting they enabled (`enabledBy`, `battle` only) and their per-person budget rows; every version of every object under `attachments/<conversationId>/<personId>/`; in Aurora mode, their own rows in the projection, through the data plane's `erasePerson`; their connector grants, when a declared connector takes them, each revoked at the vendor and then deleted through the Connectors stack's revoker (a revocation the vendor does not confirm is left `revoke-failed` for the revoker's daily retry and counted in the `offboarding` event as `connectorGrantsRevokeFailed`, so the erasure never waits on a vendor); their own tokens in `Tokens` (`reply`, `unsubscribe`, a path B `claim` and every `invitation` they issued or are named by, `PERSON_TOKEN_KINDS`); each `Identities` row, replaced in the same transaction by a `revoked` marker keyed `revoked#<issuer>#<sha256(subject)>` that holds nothing else; the AppInstanceUser; and, for this deployment's pool only and only when the account exists, `AdminUserGlobalSignOut` then `AdminDeleteUser`. A host pool's account is never deleted. A step that fails stops the run before the identity is touched (503 `OFFBOARDING_INCOMPLETE`), and every step is idempotent, so a retry continues where the last one stopped. `POST /users/delete` takes `personArn`, or `username` for an account of this deployment's pool, including one that has never signed in; the answer names the count removed from each store and what is kept. Each completed offboarding appends one `offboarding` event to the archive (the client-events Firehose, or Aurora `client_events` in Aurora mode) with the actor and subject AppInstanceUser ARNs and those counts, and each `Identities` change writes an access-log record. Neither carries an email address or a username.
- **Export by AppInstanceUser.** `POST /users/export` (`export-users`) returns one archive of everything kept about one person (GDPR Articles 15 and 20), read from the same inventory an erasure walks: one section per store of `OFFBOARDED_STORES` and then `OFFBOARDING_KEPT`, in that order, each saying whether the deployment has the store, whether the person is held in it, and its rows (`backend/lambda/src/lib/person-export.ts`, whose reader table is typed by that inventory, so a store erasure gains without a reader fails the build). It runs on `OffboardingFunction` and `OffboardingRole`, asked through user management exactly as a delete is, and reads only: that role holds the reads it needs (`GetItem` and `Query` on `Identities` and its `byPerson` index, `GetItem` on the profile and budget tables). Attachments are listed by key and size, not copied; no token, nor its hash, is exported; connector grants, the Aurora projection, battle votes, thumbs feedback and the conversation archive are sections marked **NOT BUILT**, never shown as empty. Each export appends one `export` event to the archive with the actor's ARN and the count held per store, never the content. Nothing kept is 404.
- **Never minted again.** On a miss the exchange reads the subject's marker and refuses (`PersonNotActive`, 403), creating nothing, and the resolver resolves the subject to nobody, so a token issued before the offboarding is refused as well. Re-admission is `POST /users/readmit` (`manage-users`), which deletes the marker; the subject's next sign-in is then a first one.
- **Driven by the issuer's delete events.** An EventBridge rule on the CloudTrail records of `AdminDeleteUser` and `DeleteUser`, for this deployment's pool and every other pool the trusted-issuer registry declares with lifecycle `cloudtrail-cognito` (the default for a Cognito pool), runs `backend/lambda/src/offboarding-events.ts` (`OffboardingFunction`) on `OffboardingRole`, the role the console's delete also runs on, because user management sends a console request to the same function (`backend/lambda/src/lib/offboarding-console.ts`). The records come from the platform trail, which records every management event (Identity stack, beside the roles whose use it records). The handler reads the pool's current state for the subject rather than trusting the event's name, so a replayed or out-of-order event converges: an account the pool no longer holds is offboarded, and one it still holds is left as it is. The rule hears deletes only. A disable changes nothing on the platform's side: the account is refused at its next vend, because the exchange asks the pool live (§4b, "An account disabled at its issuer"), and a session vended before it lasts at most its one-hour lifetime. While the pool reports the account disabled, `Directory.contactFor` answers no address for them, so no notice is sent and their reply tokens are refused; re-enabling restores both. A pending invitation a disabled person issued is refused, because a redemption requires a sign-in of its inviter's to be active at its issuer (`backend/lambda/src/lib/invitation-redemption.ts`); a `claim` token is redeemed by whoever holds it, once, into an account whose clearance reaches its target, and is deleted with the person it names. A daily sweep converges every subject of each pool as the backstop for a dropped event, and removes a pool account whose subject carries a marker. A `DeleteUser` record that names no pool is caught by the sweep.
- **Deactivate** - keep the `AppInstanceUser`, rename it to a placeholder + flag it deactivated, remove memberships, delete the auth user. Historical messages still attribute to a named (deactivated) author. Fits internal-collaboration (support/service/triage) where "who said what" must survive offboarding.

**Requirement either mode:** the name resolver needs a deleted/unknown-sender fallback (no blank authors). What ships is hard-delete + "Former member" only. `offboardMode` (`'delete' | 'deactivate'`) is declared on the conversation-type config (`backend/lib/config/conversation-types.ts`) as the per-type selector, and no handler reads it, so deactivate is the described alternative rather than a selectable one (FR14).

## 7. Composition

- **← Conversation Configuration** sets the `classification` this layer enforces; effective capability = **role ∧ conversation-type policy**.
- **The assistant is also an identity** - it acts as its own assistant identity (bearing an assistant identity, never a user), classification-gated like everyone else, with its behavior defined by Assistant Configuration. So the assistant lives in two pillars (Identity + Assistant Config).
- **Connectors** name a person and never authenticate one: a person a vendor names is resolved through `Identities` to their AppInstanceUser, never by email, and every human signs in through a registry issuer like anyone else ([SPEC-CONNECTORS.md](../../communication/SPEC-CONNECTORS.md)).

## 8. Security invariants

- **Bearer-pinned** - an actor can only ever act as itself, enforced by IAM and by the same construction for both kinds of principal: a person's classification role names `…/user/${aws:PrincipalTag/person}`, an assistant's acting role names `…/bot/${aws:PrincipalTag/bot}`. Neither role can be held un-pinned. The acting role's trust policy names only the vend and conditions `sts:AssumeRole` and `sts:TagSession` on the `assistant` and `bot` tags being present, `classification` equal to its own and `role` among the enabled assistant roles. A classification role's trust policy names only the exchange Lambda's role and conditions `sts:AssumeRole` and `sts:TagSession` on `person` being present and `classification` equal to its own role, so an un-tagged assumption is refused. IAM checks that `person` and `bot` are present, not their values; the values come from the exchange's validated claims and the vend's routing record. The roles that create conversations and add their members, and the router's role, reach `/bot/*` conditioned on their own classification tag, so they reach that classification's bots and no other's, and post nothing on that bearer (with drift on, the router's role also holds `AssociateChannelFlow` and `PutChannelExpirationSettings` bearing `/bot/*` with no classification condition; FR10); the channel flow's role reads on `${appInstanceArn}/*` with no condition (FR10).
- **An identity's whole lifecycle belongs to the platform** - creating and deleting an `AppInstanceUser` or an `AppInstanceBot` is a controlled capability of this platform rather than something a team does out of band, which is what lets an assistant be owned by the team that runs it without that team minting principals nobody tracks. An identity that is created and never deleted stays a valid bearer target forever, so the delete half is part of the boundary rather than housekeeping.
- **An assistant's identity is fixed before the model runs** - the routing record fixes it before dispatch and the session is adopted ahead of the model loop, so model output cannot influence which assistant a turn acts as.
- **An assistant session is a leaf** - the classification's permissions boundary denies `iam:*`, `sts:AssumeRole`, `sts:TagSession`, `chime:TagResource` and `chime:UntagResource`, so a session can neither edit its own policy nor chain into another role.
- **IDOR-safe** - identity comes only from validated token claims, never the request body.
- **Session policies only narrow** - a per-request capability set or channel scope can reduce the role boundary but never widen it (STS session-policy semantics), so it is safe to take them from the request body. Moderation and attachment capabilities are additionally refused off the admin plane.
- **Admin authority is a separate identity** - cross-channel admin reads and moderation ride the standing `${personId}-admin` identity on channel-scoped, short-lived, audited credentials, so an admin's own chat identity is membership-gated like any user's and can never silently read a conversation it is not a member of ([SPEC-ADMIN-IDENTITY.md](./SPEC-ADMIN-IDENTITY.md)).
- **Per-tenant credential isolation** for connector-resolved externals ([SPEC-CONVERSATION-TYPES.md](../conversation/SPEC-CONVERSATION-TYPES.md)).
- **Classification gating is keyed on the global `aws:ResourceTag/classification`** in a fail-closed **Allow** - Amazon Chime SDK exposes no service-specific condition keys, so a `chime:ResourceTag/...` condition would be a silent no-op. The Amazon Chime SDK calls use the `chime-sdk-identity` / `chime-sdk-messaging` SDK namespaces (see [IDENTITY-PROVIDER-GUIDE.md](../../../guides/user/IDENTITY-PROVIDER-GUIDE.md) for the identity-provider integration sample, and the model section here for the bearer pin).

## 9. Implementation

**The exchange is the sole source of a person's AWS credentials.** The deployment creates no Identity Pool, so there is no fallback.
- **Exchange:** the Lambda + API + the bearer-pinned role spectrum + full-lifecycle delete (incl. membership cleanup) are in the `${STACK_PREFIX}Identity` stack (`AgentEchelonIdentity` under the default prefix).
- **Bearer pin:** `backend/scripts/deny-test-credential-exchange.mjs` provisions a real `classification=basic` channel and demonstrates that a basic user's exchange creds can send bearing their **own** ARN but are **AccessDenied** bearing the **premium** user's ARN - only the bearer differs, so the pin (not the tag-gate) is what enforces it. `backend/scripts/deny-test-bearer-pin.mjs` checks the `person` pin on every exchange role by `iam simulate-principal-policy` and live: a session for one AppInstanceUser is refused `chime:Connect`, `chime:SendChannelMessage` and `chime:ListChannelMessages` bearing another, and a non-admin session is refused its `${aws:PrincipalTag/person}-admin` twin, for the deployment's pool and a host app's pool the trusted-issuer registry declares (written and not yet run against a deployment). The same script set proves only the exchange and offboarding write `Identities`, with the subject provisioners where a `provisioned-only` issuer is declared (`deny-test-credential-exchange.mjs`, and `deny-test-pending-identities.mjs` for what each provisioner may write) and that a foreign issuer's mapping reaches only what it declares (`deny-test-issuer-mapping.mjs`), both written and not yet run. `backend/test/the-bearer-pin-is-the-person-tag.test.ts` asserts the synthesized policies pin on `PrincipalTag/person`.
- **API contract:** `tests/e2e/credential-exchange.spec.ts` covers it (no-auth → 401; authed → own-ARN creds + classification; body-supplied sub/tier ignored - IDOR-safe).
- **Admin vend planes:** the admin-plane moderation, archive (`execute-api:Invoke`), and S3 attachment (`s3:GetObject`) session-policy vends live in the admin credential exchange (`admin-credential-exchange.ts`, in `AdminServices`), each requested on its capability's IAM-authorized route with a `channelArn` and a stated reason, and each audited; the person exchange answers an admin-plane request with `ADMIN_VEND_MOVED`. The admin exchange's unit tests (`admin-credential-exchange.test.ts`) cover all three planes (including that moderation and attachment capabilities are refused off the admin plane, and that an `attachment-read-uploads` vend is audited as `sensitive`).
- **Assistant pin:** the per-classification `ProcessorRole` holds only its bootstrap and the processor's own records; the turn runs on a session of the acting role (`assistantActingRole`): a boundary managed policy per classification, a bearer of `/bot/${aws:PrincipalTag/bot}`, trust naming only the vend and conditioned on `assistant`, `classification`, `role` and `bot`, and the vend minting the session from the router's routing record. The router's `AgentHandlerRole` holds a `/bot/*` bearer for describe, list and get conditioned on the classification tag, an unconditioned `chime:SearchChannels` on `/bot/*` and `/user/*`, and, with drift on, channel, membership and moderator creation on `${appInstanceArn}/*`; it speaks on a vended session. The live deny-tests are the three e2e specs listed in §4a, alongside `deny-test-credential-exchange.mjs`.
- **Frontend:** `VITE_PERSON_API_URL` is **REQUIRED**, and the chat client refuses to start the Amazon Chime SDK without it (`frontend/packages/chat/src/services/chimeService.ts`); the backend creates no Identity Pool. The Playwright signin + agents suites run against the frontend with no Identity-Pool fallback - the round-trip (sign-in → exchange → Amazon Chime SDK WebSocket → send → agent reply) runs entirely on bearer-pinned exchange creds.

## 10. Tag-coupled pin
The bearer pin resolves `…/user/${aws:PrincipalTag/person}` from a session tag the exchange sets on `AssumeRole`. `${aws:PrincipalTag/person}` only resolves for a credential the exchange itself vended (it is the thing that sets the tag), so a credential from any other source cannot satisfy the pin - which is why the exchange is the sole Amazon Chime SDK credential source, with no fallback.

The assistant pin is tag-coupled the same way: the acting role's bearer resolves `…/bot/${aws:PrincipalTag/bot}` from a session tag the vend sets, and only the vend may assume the role, so a credential from any other source cannot satisfy the pin. The bot's own `classification` tag is checked as a second layer. Both remain fail-closed for the same underlying reason - what a role may bear is a resource it names through a tag only the sanctioned vend can set, never a wildcard plus a check that something else has to supply.
