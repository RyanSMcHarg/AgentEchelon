# Identity and Access Model

**Status:** Partial (the groups, the three admins, the bearer pin and the classification-bound exchange ship; the person-identity contract in §1a is built and **NOT VERIFIED** on a deployment, row by row in its table).

**Coverage:** `tests/e2e/credential-exchange.spec.ts`, `tests/e2e/signin.spec.ts`, `tests/e2e/classification-context.spec.ts`

**Related:** [SPEC-CREDENTIAL-EXCHANGE.md](./SPEC-CREDENTIAL-EXCHANGE.md) (the vend) · [SPEC-CONVERSATION-SECURITY.md](./SPEC-CONVERSATION-SECURITY.md) (the layered boundary) · [ACCESS-CONTROL-BY-EXAMPLE.md](./ACCESS-CONTROL-BY-EXAMPLE.md) (the worked denials) · [SPEC-ADMIN-IDENTITY.md](./SPEC-ADMIN-IDENTITY.md) (the two-identity admin model) · [SPEC-MODERATION.md](./SPEC-MODERATION.md) (redact against delete authority)

**Site section:** Interaction layer, governance.

---

**This is a reference model, not a spec.** It carries no functional-requirements table, because it states what is true about the deployed identity and access model rather than what the platform must do. The requirements that this model satisfies live in [SPEC-CREDENTIAL-EXCHANGE.md](./SPEC-CREDENTIAL-EXCHANGE.md) and [SPEC-CONVERSATION-SECURITY.md](./SPEC-CONVERSATION-SECURITY.md).

**Who it is for, and the problem it solves.** A business that runs assistants for users at different clearance levels needs to trust - and to verify - exactly who can do what and which primitive enforces each boundary, so it can reason about isolation and map its own operators in. The alternative is to trust a product's access claims without an authoritative account, or to design, document and secure an identity-and-IAM model of its own. The audience is the platform developer and the admin / operator who need that account: a person as one AppInstanceUser whichever identity provider signed them in, the four additive groups, the three distinct meanings of "admin", and the bearer-pinned, classification-bound exchange.

**Why it exists as its own document.** "Admin" means three different things in this codebase, and two of them are easy to conflate. A person is an AWS resource, one AppInstanceUser, rather than a record in an identity provider: authority comes from the clearance and groups an issuer's record resolves to, never from which issuer or pool holds the person. The classification boundary is enforced at the credential exchange, which is the only source of a person's AWS credentials: there is no Identity Pool. Both facts are the opposite of what a reader assumes, so the account is written once here instead of being reverse-engineered from five stacks.

## 1. TL;DR

- **A person is one AppInstanceUser** ([§1a](#1a-a-person-is-one-appinstanceuser)). Every record a person makes or owns is keyed by its id, written `<personId>` below. An identity provider holds the person's email, name and credentials, and its record maps to the AppInstanceUser through the `Identities` index. Authority comes from **group membership and clearance**, resolved through `ClearanceSource`, not from which pool or issuer holds the person.
- **Four groups, additive:** `basic` / `standard` / `premium` / `admins`. A user can hold more than one; `admins` is meant to be held *in addition to* a classification (for example `premium` **+** `admins`). See [§4](#4-can-a-user-be-in-multiple-groups-yes-by-design).
- **"Admin" is three distinct things** ([§3](#3-the-three-admins)):
 1. the Cognito **`admins` group** (a claim) - gates the admin console and API, and clears the person's chat identity for admin conversations and no member conversation;
 2. the **admin console role** (`${RES_PREFIX}-admin-console`), the IAM role the credential exchange vends an `admins` member a one-hour console session on, which holds exactly the admin capabilities the catalog names;
 3. the Amazon Chime SDK **`app-instance-admin`** identities that hold cross-channel redact and delete: a dedicated **service** identity (not a human) for automated administration, plus each human admin's own **separate `${personId}-admin`** `AppInstanceUser` (their chat identity `${personId}` is never registered), whose scoped credential the admin wields client-side.
- **The frontend reaches Amazon Chime SDK *only* through the credential exchange** (bearer-pinned, classification-bound). The deployment creates no Identity Pool and no group carries a role, so there is no fallback.
- **Human admins administer CLIENT-SIDE as their own `${personId}-admin` identity.** The admin credential exchange vends a per-channel, short-lived, audited credential (`POST /exchange-credentials/admin/<capability>`) pinned to `${personId}-admin`; the console calls Amazon Chime SDK redact, delete and membership directly, attributed to the human at the Amazon Chime SDK layer and in an audit event (`admin_scoped_credential_vend`). The chat identity `${personId}` is never elevated. The dedicated service identity handles automated, no-human paths.

## 1a. A person is one AppInstanceUser

The founding principle is that every user, assistant and conversation is an AWS resource with an ARN, every actor holds a bearer-pinned identity, and access is an IAM decision keyed on an immutable classification tag. Applied to identity, it fixes the following.

- **The entities.** A human is one AppInstanceUser, an assistant is one AppInstanceBot, and a conversation is one Amazon Chime SDK channel. Every record is keyed by one of them.
- **The `Identities` index.** An identity provider holds a person's email, name and credentials. Its record maps to the AppInstanceUser through one index, `(registry issuer id, declared subject) -> AppInstanceUser ARN`. Each issuer declares its subject claim: `sub` by default, `tid` + `oid` for Microsoft Entra ID, org id + user id for Salesforce. Only the credential exchange writes the index, apart from the `pending` rows the subject provisioners write ahead of a `provisioned-only` issuer's first sign-in and the `revoked` markers offboarding leaves ([SPEC-CREDENTIAL-EXCHANGE.md](./SPEC-CREDENTIAL-EXCHANGE.md) §4b, §5b). The AppInstanceUser is authoritative, so a row whose AppInstanceUser is gone resolves to nothing.
- **An opaque id, minted once.** The credential exchange is the only code that creates an AppInstanceUser for a person. The id is opaque: it is never a Cognito `sub`, a Username or a hash derived from an issuer and subject.
- **One human, one AppInstanceUser.** No person-level link or alias table exists. A second issuer is added to a person only by a session already pinned to their AppInstanceUser plus the second issuer's token, in one call. A relation between conversations is a resource tag on a channel naming another channel, never member-writable channel Metadata. The admin-plane `${personId}-admin` AppInstanceUser (§3.3) is the one second principal a human holds: created by the exchange and tagged with its owner's AppInstanceUser ARN, so analytics, audit and erasure attribute it through the tag rather than by parsing the suffix.
- **Every signal resolves to the AppInstanceUser first**, and reaches the identity provider only from that ARN: a message (the sender ARN), a meeting attendee (`ExternalUserId` is the AppInstanceUser id), a transcript segment (through its attendee or call leg), a call leg, a voicemail, an invitation, an inbound reply and an outbound recipient.
- **Email and phone are delivery routes, never identity.** An address may find a record inside one issuer's directory. It never binds, merges or creates an identity, and an inbound call is never matched to a person by phone.
- **One resolver on the server.** The caller is resolved once per request: at the edge authorizer for a token-authorized route, or from the vended session's role session name for an IAM-authorized route. Handlers never read `claims.sub`, `cognito:username` or `claims.email`.
- **One seam per lookup.** Groups and clearance go through `ClearanceSource`. Rosters, names and contact addresses go through `Directory`, keyed by AppInstanceUser: each issuer's registry entry declares a `directory` adapter (`cognito`, `claims` or `none`; `identity-store`, `graph`, `connector:<id>` and `scim` are **NOT BUILT** and refused at synth) that reads the issuer's own store live, every lookup starts from the AppInstanceUser ARN, and a name or address is fetched per use and never copied, except under `claims`, which records the last sign-in's contact claims against the ARN for an issuer with no directory and is erased with the person ([SPEC-CREDENTIAL-EXCHANGE.md](./SPEC-CREDENTIAL-EXCHANGE.md) §4b).
- **The client's identity is the `userArn` the exchange returns.** The client never decodes the ID token to build an ARN.
- **An AppInstanceUser may exist before its person signs in.** Pending and guest AppInstanceUsers are created by the exchange with an expiration. A guest's AppInstanceUser has an `Identities` row under the guest issuer from its first message. A pending invitee, one the deployment does not yet know, has no `Identities` row until redemption binds one; a single-use token names its AppInstanceUser until then. Whether binding can remove the expiration is **OPEN**; if it cannot, pending invitees are created without an expiration and a low-frequency sweep deletes AppInstanceUsers whose invitation expired unredeemed. The sweep is time-based because the absence of an event cannot be event-sourced (tenet D6).
- **Erasure runs by AppInstanceUser over every store**, for every issuer. Battle votes and feedback stay on delete, carrying the AppInstanceUser id.
- **Adding an issuer widens authentication only, never authorization.** The vend still pins the bearer to the AppInstanceUser, and IAM still evaluates `classification` on every channel action, so a token from any issuer reaches exactly the classification set its issuer's declared mapping grants. Those sets need not nest: the shipped `basic`, `standard` and `premium` nest only because the sample is configured that way, and the outside `customer` classification grants only itself, so a member cleared for all three does not reach it.

**As built.** The credential exchange mints each person's AppInstanceUser id as a UUID v7, so it never equals a token's `sub`, and no handler derives the caller from a token: `backend/test/a-person-is-their-app-instance-user.test.ts` refuses a read of `claims.sub`, `cognito:username`, `claims.email` or `cognito:groups` outside the resolver, the exchange and the edge authorizer.

Two facts most readers get wrong, both verified in code:

1. **There is no Identity Pool, and no group carries a role.** `identity-stack.ts` creates the clearance and membership groups with no `RoleArn`, and nothing assumes a role from a group: every credential a person holds is vended by the credential exchange. So holding the `admins` group grants nothing by itself; it is the claim the exchange reads before it vends a console session.

2. **The classification boundary lives on the credential-exchange classification roles.** `exchangeVendStatements` applies `classificationChannelScopedAllow(token, …, { actor: 'person' })` to every classification's vend role (the `ExchangeRole` construct, `backend/lib/constructs/exchange-role.ts`, built by each classification's own `Assistants-<classification>` stack, and by `identity-stack.ts` for the admin plane), each **bearer-pinned** to `…/user/${aws:PrincipalTag/person}`. This is the same fail-closed tag-gate the specs describe, attached to the exchange role, the only role a person's chat credential is on.

**One resolver for the Claim row.** The credential exchange and `auth.ts` both resolve a caller's classification through the profile registry: `ProfileRegistry.clearanceForGroups` unions the grant sets the caller's groups clear for and finds the declared classification whose own grants ARE that union ([ADR-046](../../../design/decisions/046-classifications-are-a-set-not-a-ladder.md)), and an issuer's declared clearance source is read through `holderTokenOf`. No fixed group order exists. The app-layer guard that matters most, `callerIsAdmin`, does not read `clearance` at all - it is a separate any-match check on the admin group names (§4).

## 3. The three "admins"

They share a word and nothing else, and the model does not make sense unless they are kept separate.

### 3.1 Cognito `admins` **group** - a claim
- **What it is:** membership in the `admins` Cognito group, surfaced as a value in the `cognito:groups` JWT claim.
- **What it unlocks:**
 - **The admin console and admin APIs.** `callerIsAdmin(event)` / `requireAdmin` check `parseGroups(claims['cognito:groups']).some(g => ADMIN_GROUPS.has(g))` (`auth.ts`). The default admin group name is `admins`, overridable via `ADMIN_GROUP_NAMES` for host-app integrations (`auth.ts` `ADMIN_GROUPS`, see `ADMIN-INTEGRATION-GUIDE.md`).
 - **The admin plane's chat role is tag-gated like every other.** The `admin` vend role reaches admin-plane channels only, bearer-pinned to the admin's own user; a person holding `admins` beside a member classification is vended that classification's role with the `adminPlane` session tag, which adds admin-plane channels and nothing else. No chat credential reaches every classification: reading any conversation is admin access, through the console and the `${personId}-admin` identity ([SPEC-ADMIN-IDENTITY](SPEC-ADMIN-IDENTITY.md) FR1).
- **What it does NOT grant:** message **delete or redact**. The chat action set (`EXCHANGE_MSG_ACTIONS`, `backend/lib/constructs/exchange-role.ts`) carries no `UpdateChannelMessage`, `RedactChannelMessage` or `DeleteChannelMessage`. Deleting or redacting others' messages requires the admin's separate `${personId}-admin` identity, vended per channel by the admin credential exchange on a per-capability route (§3.3), never the chat role.
- **Who assigns it:** added to the group explicitly, not derived from `custom:tier` (the post-confirmation trigger only mirrors *classification* into its matching group). `admins` is additive - held **alongside** a classification.

### 3.2 The admin console role - an IAM role vended per sign-in
- **What it is:** `${RES_PREFIX}-admin-console` (`ADMIN_CONSOLE_ROLE_NAME.admins`, `admin-services-stack.ts`), assumed only by the admin credential exchange, for an hour, as `console-<personId>`, when an `admins` member asks it for `identity: 'console'`. Its sibling `${RES_PREFIX}-team-console` serves `team-members`.
- **What it grants:** exactly the admin capabilities the catalog gives the role (`backend/lib/config/admin-capabilities.ts`), granted by name on each admin API (`grantAdminRolesOnApi`). It holds no Amazon Chime SDK bearer: moderation is the separate `${personId}-admin` identity (§3.3).

### 3.3 Amazon Chime SDK `app-instance-admin` - service AND per-human identities

See [SPEC-ADMIN-IDENTITY.md](./SPEC-ADMIN-IDENTITY.md) for the full model. Two kinds of app-instance-admin exist:
- **The service app-instance-admin:** a single dedicated **service** `AppInstanceUser` (`AppInstanceUserId = agent-echelon-admin`), created and registered as an `AppInstanceAdmin` by the `create-app-instance-admin.ts` custom resource; ARN in SSM (`/agent-echelon/app-instance-admin-arn`). Not a human, not tied to any Cognito user. It is used for **automated, no-human** administration, for example membership-audit auto-revoke.
- **Per-human admin identities:** each human admin has a SEPARATE `${personId}-admin` `AppInstanceUser` registered as an `AppInstanceAdmin` (their chat identity `${personId}` is never registered). Human-initiated moderation runs **client-side** from the admin's own browser, using the `${personId}-admin` bearer, vended per channel, short-lived, and audited by the admin credential exchange (`POST /exchange-credentials/admin/<capability>`). It is attributed to the human at the Amazon Chime SDK layer and revoked per person.

**What either holds:** cross-channel **redact AND delete**. The `${personId}-admin` identity is the only principal with an IAM grant for `RedactChannelMessage`: a human channel moderator's chat role and every assistant role carry no such grant, whatever Amazon Chime SDK's moderator model would permit, and neither can delete.

**The admin identity's credential is a browser credential; the service one is not.** The admin credential exchange vends the `${personId}-admin` admin-plane credential to the admin's browser only on a per-capability route signed with a console session: scoped to one channel, short-lived, and recorded as `admin_scoped_credential_vend`. The admin console then calls Amazon Chime SDK redact, delete and membership directly (`frontend/packages/admin/src/services/adminChime.ts`). The chat identity `${personId}` is never vended admin-plane credentials. The service app-instance-admin is used only for no-human automation. Attribution is native at the Amazon Chime SDK layer (the human's own `${personId}-admin` ARN) **and** in the audit trail.

### 3.4 The Amazon Chime SDK implicit-role model (the layer beneath admin #3)

The three "admins" above are AgentEchelon's constructs. Underneath, Amazon Chime SDK Messaging enforces its **own** authorization model - the "implicit roles" - that operates *in addition to* IAM. Understanding it is what makes §3.3 precise, and it is why a **service** `app-instance-admin` is the right and necessary tool for cross-channel administration.

**Implicit roles are a second, independent gate.** Authority is a function of the caller's **role relative to the channel** (AppInstanceAdmin / ChannelModerator / Member / Non-member), enforced by the Amazon Chime SDK back end regardless of what IAM says. From the AWS authorization-by-role reference ([`chime-sdk/.../auth-by-role.html`](https://docs.aws.amazon.com/chime-sdk/latest/dg/auth-by-role.html)), the meaning of a **Denied** cell is explicit:

> **Denied** - *Even if the correct Action/Resource context is specified in the IAM Policy, it will still be blocked by the back end.*

So **IAM-allowed is necessary but not sufficient.** Two gates stack:

1. **IAM** decides which `x-amz-chime-bearer` ARN a caller's credentials may name (the call is performed **as** that `AppInstanceUser` or `AppInstanceBot`). Here the credential exchange **pins** the bearer to the caller's own AppInstanceUser id (the `person` session tag carries it), so a caller can only ever act as themselves.
2. **Amazon Chime SDK's implicit-role model** then decides what that bearer may do on the target channel - and can **deny even when IAM allows**.

| Implicit role | Scope | Can | Cannot (Amazon Chime SDK denies even if IAM allows) |
|---|---|---|---|
| **AppInstanceAdmin** | Every channel in the app instance; **no membership needed** to moderate | `ChannelModerator` actions on **all** channels; `RedactChannelMessage`; **`DeleteChannelMessage`**; manage members, moderators and bans | `SendChannelMessage` **without first joining** (must `CreateChannelMembership` for itself to send); edit *others'* messages (`UpdateChannelMessage` = own only) |
| **ChannelModerator** | Only channels it moderates | add and remove members and moderators, manage bans, **`RedactChannelMessage`**, list messages, `UpdateChannel` / `DeleteChannel` | **`DeleteChannelMessage` = Denied**; anything in channels it does not moderate |
| **Member - `DEFAULT`** | Only channels it belongs to | `SendChannelMessage`, read; redact and update **own** messages; add members **only in an `UNRESTRICTED` channel** | `DeleteChannelMessage`; moderator actions; add members in a `RESTRICTED` channel |
| **Member - `HIDDEN`** | Same, read-only | read and observe; **invisible** in `ListChannelMemberships` | **`SendChannelMessage`** (Amazon Chime SDK-enforced) |
| **Non-member** | - | only PUBLIC-channel describe and list | send, read or moderate on any channel unless it is also Admin or Moderator |

Two channel properties shape the Member rows: **`Mode`** (`RESTRICTED` → only moderators add or remove members; `UNRESTRICTED` → members can too) and **`Privacy`** (`PUBLIC` → non-members can describe and list; `PRIVATE` → invite-only, opaque to non-members). AgentEchelon creates conversation channels `RESTRICTED` + `PRIVATE`.

**Redact against delete - the exact semantics this platform relies on:**
- `RedactChannelMessage` → **tombstone**: the message "exists in the back end, but the action returns null content, and the state shows as redacted" (`Redacted=true`). **Moderator or admin** can redact any message; a member can redact their **own**.
- `DeleteChannelMessage` → **removal**: "Deletes a channel message. **Only admins can perform this action.** … A background process deletes any revisions created by `UpdateChannelMessage`." **AppInstanceAdmin-only** - `ChannelModerator` and `Member` are both **Denied**.

**Why this forces the service-admin design.** The admin console reviews **every** conversation across all classifications. To act on an arbitrary channel it needs an identity that (a) can `DeleteChannelMessage` at all - which **only** an AppInstanceAdmin can - and (b) can redact or manage a channel **without first being added to it** (admins moderate membership-free; only *sending* would require a join). A per-classification assistant (AppInstanceBot) is only a moderator of its **own** channels; a human admin promoted to per-channel moderator would still be **delete-incapable** and would have to be added to each channel first. The service `app-instance-admin` satisfies both for automated paths, and each human admin has a separate `${personId}-admin` identity registered as an `AppInstanceAdmin` so their own client-side administration satisfies both as themselves, each an auditable Amazon Chime SDK identity (§3.3). An `AppInstanceAdmin` is required for delete regardless of who acts.

## 4. Can a user be in multiple groups? Yes, by design

Groups are **additive**, and that is the intended model:

- **`admins` is meant to be held *with* a classification.** An operator is typically `premium` **+** `admins`: `premium` for what their *own* conversations can do, `admins` for admin conversations and, through an issuer declaring `admin: true`, the console. The classification signal is the declared classification whose grants equal the union of what the person's groups clear for (`ProfileRegistry.clearanceForGroups`), and `isAdmin` is a *separate* any-match check (`auth.ts` `isAdmin`) - so holding both is coherent: the person gets admin-console access **and** a concrete data-plane classification, vended as that classification's role with the `adminPlane` session tag.
- **Conversation membership and assistant access are per-channel**, gated by the channel `classification` tag, which IAM checks on every send and `router-agent-handler.ts` answers at - independent of how many groups a person holds. Being in `admins` does not silently upgrade the assistant in a `basic` channel.
- **Admin-only conversations** are ordinary channels whose membership happens to be all-admins; there is no separate "admin channel" primitive. For the admin-conversation and email-notification pattern, see [ADMIN-GUIDE.md](../../../guides/admin/ADMIN-GUIDE.md).

> **Multi-group parsing.** `parseGroups` (`auth.ts`) strips surrounding brackets and splits on whitespace **or** commas, so the three real claim shapes (a JSON array, `"admins,premium"`, and the bracketed multi-group form API Gateway emits, `"[admins premium]"`) all parse. A `premium` + `admins` user therefore passes `callerIsAdmin`. Pinned by a unit test, `backend/test/lib/auth.test.ts`.

## 5. Admin authority and pools

A common question is why admin authority is not a pool boundary. The answer, and the reasoning:

- **Group as authority, not pool or issuer.** Admin power is a *claim* (`admins` group) evaluated at the API layer, not a pool boundary. A person who is both a user and an operator is one AppInstanceUser (§1a), and host-app integrations map their own admin role in via `ADMIN_GROUP_NAMES` or federation (`ADMIN-INTEGRATION-GUIDE.md`).
- **Staff and customers are separate issuers.** Which pool a person signs in through decides who may hold a record there, not what the record grants. A deployment whose customers self-register declares a staff pool (no self sign-up, SAML only, for example from IAM Identity Center) apart from its customer pool, so a self-registered customer never sits in the pool that holds administrators. Both resolve to AppInstanceUsers the same way. The trusted-issuer registry declares each pool (`backend/lib/config/issuers.ts`). **NOT BUILT:** a second pool of the deployment's own; the deployment creates one pool, and a further pool in the registry is an existing pool it trusts, for example a host app's pool whose people reach only the one-conversation session.
- **The strong separation is at the *identity plane*.** An admin's ordinary (chat) browser credential can never act as an admin: it is pinned to `${personId}`, which is **not** an app-instance-admin, and the exchange never vends it a delete or redact action. Admin authority lives on a SEPARATE `${personId}-admin` identity, and the admin credential exchange vends its credential only on a per-capability route signed with a console session: scoped to one channel, short-lived, and recorded (`admin_scoped_credential_vend`). So the blast radius of a stolen admin browser session is bounded to what the exchange vends per request, one channel at a time and each vend audited, and admin actions are attributed per human at the Amazon Chime SDK layer (the `${personId}-admin` ARN), not only in the app audit trail.

## 6a. Full access matrix - assistants and context (data plane)

§6 covers the **channel** plane (who can act on a conversation). This section adds the **data plane** - which *context* each identity can read - and the **assistants**, which §6 only touched. Verified against code (classification stacks and processors); caveats are flagged in the notes below.

**How a user reads context depends on the use case.** In *this* deployment, users have no direct `s3:GetObject` on `context/*` (there is no Identity Pool, and the exchange roles grant only Amazon Chime SDK message actions), so a user's access to knowledge is mediated by (a) *which assistant* sits in their channel - the channel's classification, which IAM only lets them send into where their own classification grants it - and (b) *what that assistant is allowed to read*. So here, "what can a Basic user learn from the assistant" is answered by the **Basic assistant's row**, not the Basic user's.

> **This is not the only shape - it is one of several the substrate supports.** The `context/{classification}/` store is a **role-tiered knowledge source**, and the same prefix structure is meant to be pointed at whatever the deployment's knowledge *is*. In many use cases that source is content users **also** read directly, by the **same role**: a wiki, a docs site, or **published posts**. A sibling reference deployment wires exactly this - a context-sync function syncs published blog-post summaries into the same tiered prefixes (`…/blog-posts-public.json` for the public or guest role, `…/blog-posts.json` for the authenticated role, an admin variant for everything), so the **assistant** reads the posts from S3 while **users** read the very same posts through the app, each gated by role. There, context is a *shared, role-gated* store rather than an assistant-only one. AgentEchelon-Public ships a **seeded placeholder** (`context/{classification}/*.json` sample company context) with that structure in place, ready to be pointed at a real published-content or wiki source. The invariant that holds across all shapes is the **role and classification gate** (`context/{classification}/`), not "who" reads it - assistant, user, or both, according to role.

### Table B - Assistant capabilities and context access

Per-classification assistant (a session of the classification's assistant acting role, acting as one **bot** identity; the async processor's own role holds only its bootstrap and its own records about a turn, which the session cannot write). ✅ = allowed · - = denied.

| Capability / resource | Basic asst | Standard asst | Premium asst | Enforced by |
|---|:--:|:--:|:--:|---|
| Send/read on channels of **exactly its own classification** (bot bearer, tag-gated; ADR-042) | basic | standard | premium | `classificationChannelScopedAllow` with `actor: 'assistant'`, which resolves to `channelsAnAssistantMayActIn` - own classification alone (`agent-classification-common.ts`); the bearer statement is `/bot/${aws:PrincipalTag/bot}` with the bot's `classification` tag equal to the role's own, so a session reaches one bot of its own classification (`assistantActingRole`, [SPEC-CREDENTIAL-EXCHANGE.md](./SPEC-CREDENTIAL-EXCHANGE.md), the assistant pin) |

| Embeddings (`amazon.titan-embed-text-v2`) | ✅ | ✅ | ✅ | `bedrock:InvokeModel` scoped to titan-embed (`agent-classification-common.ts`) |

**An assistant's CONTEXT reach and its CHANNEL reach are deliberately different.** ADR-042 narrowed the channel boundary to the assistant's own classification; the context read stays the set that classification grants, which is why the premium row reads all three prefixes and only the premium channel. `backend/test/cdk-synth.test.ts` (case 'gives the assistant the SAME reach for channels and for context prefixes') keeps both derived from one resolver so they cannot drift apart independently.

**Users, by contrast (data plane), in this deployment:** **no** direct `context/*`, `attachments/*`, `generated-docs/*`, `battle-images/*`, or KB read; users see context only as prose the assistant writes back into the channel. **This is deployment-specific, not a law of the design** - see the shared-knowledge note above: a use case whose context is a wiki or published posts grants users direct, role-gated read of the same source. The service `app-instance-admin` also has **no** context or KB grant - it reviews history through the analytics **archive** (Athena or Aurora), a separate admin-only role, not the context store.

**Notes and verified caveats:**
- ¹ **KB retrieval is live only in Aurora analytics mode** (`ENABLE_LIVE_DRIFT`); in Athena mode no KB or drift path is wired. "On by default" means *when Aurora is deployed*.
- **KB classification filter.** Ingestion stamps `metadata.classification` via `deriveContentClassification` (from the `rag/{sourceType}/{classification}/` prefix; default `RAG_DEFAULT_CLASSIFICATION`, or failing that `failClosedContentValue`, the conversational classification the fewest holders reach), and retrieval filters on `metadata->>'classification' = ANY($3)` (`document-retrieval.ts`) with no `IS NULL` branch, so untagged chunks are not returned. Pinned by `backend/test/lib/document-ingestion-classification.test.ts`. Aurora-mode only; the filter is classification-only (there is no finer-grained per-document `visibility` field).
- **The context prefix is chosen from the assistant's own classification, not the channel's.** Net access is correct because ROUTING binds the classification-matched bot to the channel. IAM enforces the equality on the CHANNEL side: an assistant's channel grant is its own classification alone, so an assistant placed on a channel of any other classification is denied every channel action there ([ADR-042](../../../design/decisions/042-an-assistant-acts-in-exactly-one-classification.md), deny-tested by `tests/e2e/assistant-classification-boundary.spec.ts`). What remains an application property is the CONTEXT side: the prefix is chosen from the assistant's own classification rather than read back from the channel, so the two agree because routing binds a classification-matched bot to the channel, not because a policy compares them.
- **Context-aware model routing runs on the standard classification only** (`contextRouting: true` in the standard classification's `topology` in `lib/config/profiles.ts` alone); basic and premium use the classification-default model. **The configurable intent pack is provisioned for all classifications** (`intentPackParam: true` in all three profile stacks). The A/B experiment override, per-classification default model, and the separate Haiku classifier **are** wired on all classifications.
- **Attachment reads are ownership-checked.** Both the standard processor and the premium `/battle` vision path verify the sender owns the referenced attachment `fileKey` (`senderOwnsAttachmentKey`) before reading from `attachments/*`, falling back to text-only on a cross-user reference, even though the IAM `s3:GetObject` grant spans `attachments/*`.

## 6b. Defense in depth - guardrails are one layer, not the boundary

A recurring mis-read is to treat Bedrock Guardrails as *the* enforcement. They are not - they protect the **assistant's** input and output. The conversation, and the data boundary, are defended by several independent layers, most of which run **whether or not an assistant is involved**. If any one layer fails, the others still hold.

| Layer | Protects | Runs on | Mechanism | Where |
|---|---|---|---|---|
| **IAM + `classification` tag** | Which conversations a principal may read or send in | **every** Amazon Chime SDK call | Fail-closed ALLOW on `aws:ResourceTag/classification`; provable with a deny-test | §2 |
| **Credential exchange (bearer pin)** | Impersonation - a caller acts only as **itself** | every user Amazon Chime SDK session | STS `person` session tag pins the bearer to `…/user/${personId}` | §2 |
| **Bedrock Guardrails** | **Assistant** turns: input (prompt-injection, content) and output (PII, content, markers) | assistant turns **only** | `ApplyGuardrail` `source: 'INPUT'` before the call **and** `source: 'OUTPUT'` after; fail-open | [SPEC-CONVERSATION-SECURITY.md](./SPEC-CONVERSATION-SECURITY.md), Layer 5 |
| **Channel flow** | Conversation-level message handling - **runs on every message, including human-to-human with no assistant** | every message in a channel (before Lex) | Amazon Chime SDK `CHANNEL_FLOW` processor; must `ChannelFlowCallback` to release, so it can hold, modify or deny any message. Carries mention and `@all` routing, battle orchestration, notify directives and idempotency, and is the conversation-level interception point where content rules can run | [MESSAGE-FLOW.md](../../../guides/developer/MESSAGE-FLOW.md) |
| **Archival + proactive analysis** | Catching failures **after the fact** - classification mismatches, drift, security events | async, **all** Kinesis events | Archive of every channel event + drift detection + `[SecurityEvent]` logging over the archive. Aurora mode; report-only by default - it detects, logs and alerts, and the membership audit auto-revokes only when its runtime enforce toggle is on (the `config/enforce` item in the audit table, flipped from the admin console's Security tab; `-c membershipAuditEnforce=true` sets only the default) | [SPEC-CONVERSATION-SECURITY.md](./SPEC-CONVERSATION-SECURITY.md), Layer 6 |

Two things this makes explicit:
- **Guardrails only see assistant turns.** A human-to-human message in a shared channel is not guardrailed - but it *is* subject to the IAM and classification boundary, passes through the channel flow, and is archived for proactive analysis. So "no assistant involved" is not "no enforcement".
- **The provable boundary is IAM**, not the model layer. Guardrails and the channel flow are content and behavior defenses on top of the data boundary; the thing that *cannot* be bypassed by an application bug is the fail-closed IAM tag gate (§2), and the archival layer is the independent backstop that catches anything the inline layers miss.

## 7. End-to-end: an admin deletes a message outside their own classification

1. Operator signs in through the deployment's issuer; the JWT carries `cognito:groups = premium, admins`.
2. The frontend calls the credential exchange and gets **chat** credentials on the `premium` role with the `adminPlane` session tag: bearer-pinned to the operator's own user, reaching the channels `premium` grants plus admin conversations, **no** delete or redact. Reading any other conversation is the admin console's archive read, not this credential.
3. The operator opens the admin console and clicks "delete message". The SPA requests a delete credential from the admin credential exchange (`POST /exchange-credentials/admin/delete`), scoped to that one channel.
4. The exchange verifies the `admins` claim (`auth.ts`), provisions or uses the operator's `${personId}-admin` identity, and vends a short-lived credential, recording `_auditEvent: 'admin_scoped_credential_vend'`.
5. The SPA calls Amazon Chime SDK `DeleteChannelMessage` **directly, as the operator's own `${personId}-admin` ARN** (`frontend/packages/admin/src/services/adminChime.ts`). Only an `AppInstanceAdmin` can delete, and the `${personId}-admin` identity holds that authority.
6. Amazon Chime SDK attributes the action to the operator's own `${personId}-admin` ARN; the scoped vend is recorded in the audit trail with the operator's AppInstanceUser id.

The operator's *chat* credential never held delete power (step 2): the authority lives on a separate `${personId}-admin` identity, vended one channel at a time, short-lived, and **audited on every vend**.
